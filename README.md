# Loop Engine

AI に実装を任せるループを、テストの自己申告や権限逸脱に頼らず運用するための実験的な実行基盤です。

このプロジェクトでは、仕様と受け入れ条件を作る **プランナー**、関門を機械的に適用する **ランナー**、隔離環境内で実装する **ソルバー**を分離します。合格基準を作る主体と、それを満たす主体を分け、テストが実装前に失敗すること（Red）と実装後に成功すること（Green）の両方を確認します。

> [!IMPORTANT]
> ランナーは実装済みで、**要件6行から11ステップを人間の介在ゼロで通し切った実行**があります（2026-08-21）。
> その後、**同じ計画をローカルの 9B モデルで走らせても結果が変わらない**ことを確認しました（2026-09-01）。
> ただし検証手段は Python + pytest に固定されており、他言語への一般化、人間による事後監査（REVIEW_GATE）、
> 実用的な題材での検証は未着手です。

## 仕組み

| 役割 | 想定する実体 | 責務 |
|---|---|---|
| プランナー | Windows 側の Claude Code | 仕様、受け入れ条件、実行計画を作る。実装コードは書かない |
| ランナー | 通常のプログラム（`runner/loop.py`・標準ライブラリのみ） | Red、テスト凍結、検証、リトライ、エスカレーションを機械的に管理する |
| ソルバー | WSL2 内の**差し替え可能なバックエンド**（Codex CLI / ローカルモデル） | 渡されたブリーフを基に実装する。テストや計画にはアクセスしない |

ランナーが**エージェントではなく普通のプログラム**であることは、この構成の要点です。関門に価値があるのは、それが judgement を行わないからです。「惜しい」という理由で失敗を通す余地をコードのどこにも置いていません。

中心となる原則は次のとおりです。

- 受け入れ条件を作る者と実装する者を分ける
- 実装前にテストの Red を確認する
- 実装中はテストを凍結する
- リトライ上限への到達を、失敗ではなくプランナーへの差し戻しとして扱う
- ステップ間の情報はソースコードではなく contracts で受け渡す
- 人間への確認条件を事前に固定する
- ソルバーに sudo やホストへのアクセスを与えない

## 動作実績

題材はアイドルゲームの中核ロジック。**入力は要件6行だけ**で、計画の作成から実装、検証、コミットまでをループが行います。

**run 5 と run 6 — 同じ計画、ソルバーだけを入れ替えた統制実験**

run 6 は run 5 の `tasks.json` をそのまま流し、ソルバーを Codex から**ローカルの
Qwen3.5-9B**（nonthinking / IQ4_XS / RTX 2060 6GB / 41.6 tok/s）に替えたものです。
題材・計画・ランナーは同一で、差分はソルバー1つ。

| | run 5（Codex） | run 6（ローカル 9B） |
|---|---|---|
| 無介入の緑 | 11/11 | **11/11** |
| ステップあたりの試行 | ほぼ1 | **1**（全ステップ 1 attempt） |
| エスカレーション | 1回（プランナーが自分で解決） | **0** |
| 実行時間 | 19分37秒 | **15分12秒** |
| 最終スイート | 48件パス・skip 0・回帰 0 | 同左 |
| 人間の介在 | **ゼロ** | **ゼロ** |

計画の作成は run 5 で15分02秒（自己修正が1回発動し、2回目で通過）。run 6 は同じ計画を
使うため計画の作成を行っていません。

**弱いソルバーでも結果が落ちなかったことが、この構成の主張そのものの検証になっています**
── 合格基準を外に置けば、それを満たす側の質は結果を支配しない。実装 268 行を目視で
確認し、テストを通すためのハードコードは1件もありませんでした。

これ以前にも 10ステップ緑を2回（run 1 / run 2）、コールドスタートをプランナーが自力で解いた run 3 があります。各実行の全イベントは台帳（`plan/ledger.jsonl`）に `RED_GATE` / `FREEZE` / `VERIFY` / `GREEN` / `ESCALATED` として記録され、後から検証できます。

## 適用範囲

**現状は Python + pytest を検証手段とする題材に限られます。** 題材そのものには依存していません（`loop.py` に題材固有の記述はありません）が、合否の判定を pytest の JUnit XML から読む、環境を `.venv` として凍結する、といった前提が入っています。

言語に結合している箇所は**9か所に集中**していることまでは分かっています（主なものはテスト起動と判定 / 赤の判定 / `provides` の名前抽出 / 環境凍結 / コードの置き場 / `environment_facts` / 契約の型構文（L14））。2言語目には TypeScript を想定していますが、**アダプタとして切り出すのは2つ目を実装したあと**の予定です。1つしかない状態で抽象化すると必ず外すためです。

## 環境構築について

対象環境は Windows 上の WSL2 `Ubuntu-24.04` です。構築作業はホストや WSL の設定、SSH 鍵、ユーザー権限、ネットワーク制御を変更します。コマンドを抜粋して実行せず、先に [provision/README.md](provision/README.md) の前提、手順、既知の落とし穴を通して確認してください。

WSL2 は既定のままでは隔離環境ではありません。この構成では Windows ドライブの自動マウント、Windows 実行ファイルとの相互運用、WSLg を明示的に無効化し、プロビジョニング後に状態を検証します。
