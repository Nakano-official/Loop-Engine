# REDESIGN.md — 層を明示し、ループを1つのプログラムに入れる

> **状態: 提案。未実装。**
>
> **この変更は過去の失敗への対処ではない。** 現行アーキテクチャが完璧に動く前提を置いた
> うえで、「層を明示したほうがブラッシュアップの際により高度な結論が得られる」という
> 見立てから出た設計である。既存の run は**根拠ではなく事例**として参照する。
>
> 現状の形は [ARCHITECTURE.md](ARCHITECTURE.md)。この文書はそこから**何を変えるか**を述べる。

## 1. 変えること

| # | 変更 |
|---|---|
| 1 | **要件分析**の層と**要件定義**の層を置く（分けるか統合するかは未決） |
| 2 | **設計の層**を置く。定義から「どんなモジュールが必要か」を分析して書く |
| 3 | **テスト第一主義**。テストを先に書き、ソルバーはそのテストに沿って実装する |
| 4 | **実行を1つのコードで終わらせ**、その中でループが回る形にする |
| 5 | 開発モデルとしては**インクリメンタル開発 ＋ テスト第一主義**。ウォーターフォールに沿うが、**ループが回る点で違う** |

粒度の勾配として言い直すとこうなる ──
**要件を分析し、そこから「どんなモジュールが必要か」という一段深い粒度の定義を起こし、
その粒度に合わせたテストを書き、テストからコードが書かれる。** 各層は上の層に依存する。

3 の狙いは明言されている ── **ソルバーが作る範囲を狭めることで、ハルシネーションと
SLM のような弱いモデルでも質を上げられるかを調べる**こと。目的は設計の美しさではなく
**測定**であり、この文書もその観点で書く。

## 2. なぜこの形のほうが良いのか ── 結論の解像度

機構が完璧に動く前提を置くと、層の価値は「欠陥を防ぐこと」ではなく
**欠陥を切り分けられること**に全部移る。そこがこの変更の主な論点である。

いまの系で結論を書くと、こうなる。

```
run 7 の結論:「要件に穴があった」
```

**これが現行アーキテクチャで書ける最も細かい文**である。実際には4つの別物が1つの箱に
潰れている。

- 誰も「プレイヤーは最初に何をするか」を**分析しなかった**のか
- 分析はされたが**定義に書かれなかった**のか
- 書かれたが**モジュールに割り当てられなかった**のか
- 割り当てられたが**その経路をテストしなかった**のか

4つの異なる欠陥で、**4つの異なる直し方**である。層が4つしかないので、箱も4つしかない。

> **結論の解像度は、層の粒度で上限が決まる。**
>
> だから層は検査を増やすためのものではなく、**対照（control）を増やすためのもの**である。
> 検査付きで分かれた層は、上流を固定して1つだけ変えられる場所になる。

### 新しく書けるようになる結論

**(1) モデルの寄与を分離できる。** いま上流は「人間が書いた1文書 ＋ プランナー1回」なので、
出来の悪さをモデルに帰属させられない。層が検査付きで分かれていれば
「要件は正しく分析され、正しく定義され、正しく分解され、テストも正しく導かれた ──
**落ちたのは実装だけ**」と書ける。これはモデルについての結論であり、いまは原理的に書けない。

**(2) 層ごとに書き手を差し替えられる。** 関心は「弱いモデルはどこまでの範囲を持てるか」
にある。モジュール設計が独立した層になれば

```
強モデルがモジュール設計 ＋ 弱モデルがそれ以降
弱モデルがモジュール設計 ＋ 強モデルがそれ以降
```

を比較できる。いまの `tasks.json` はモジュール設計と順序決定を暗黙に同時にやっているので、
**この問いを立てることすらできない。**

> この変更は「より良いエンジン」ではなく、**より細かい計測器**である。

**(3) ブラッシュアップの単位が層になる。** いま再入できるのは `reset`（run 全体）か
`plan refine`（計画全体）だけで、「要件5だけ再分析する」が無い。層があれば、
**戻る距離が変えた情報の量に比例する。**

### 事例（根拠ではなく、形の確認）

run 7 の死因は**どのモジュールの中にも無かった** ── `production_rate` は合計として正しく、
`buy_generator` は残高不足を正しく拒否し、`view` は買えないボタンを正しく無効にした。
欠けていたのは「最初の資源を得る経路」で、**どのモジュールにも属さない性質**だった。

run 8 の S1 の `app.ts` は**作られ、テストされ、出荷物から呼ばれなかった。**

どちらも「モジュールの構成」が誰の担当でもない形をしている。

## 3. 層の検査は、下流を見てはいけない

**各層の出力に機械が読める検査が付くか。** ここが答えられないと、変更 1・2 は層を2つ
増やすだけで終わる。

この系の既存の層にはそれぞれ検査がある。

| 層 | 出力 | 検査 |
|---|---|---|
| 計画 | `tasks.json` | リンタ L1〜L15 |
| テスト | `tests/*` | RED_GATE R1〜R5 |
| 実装 | `src/*` | VERIFY |

散文を出力にすると、この計画が3回踏んだ穴に落ちる ──

> **書いていないことは伝わらない。そして検査されない散文は、書いていないのと同じ。**
>
> L15（契約がモジュール名を言わなかった）、欠陥4（起動経路を誰も検査しなかった）、
> run 7 の S10（プランナーが直し方を `goal` に900字書き、テストは `acceptance` から
> 起こされるので届かなかった）。

### 判定基準

候補を増やす前に、落とす条件を決めたほうがよい。

> **層の検査は、次の層の出力を参照してはいけない。** 参照したら、その2層は1つの箱に戻る。

同じ run 7 の欠陥に当たる2つの候補で、合否が分かれる。

| 候補 | 判定 |
|---|---|
| 各要件が**どの受け入れ条件に覆われるか**を要求する | **不可。** 計画を読む検査なので、要件定義の層は独立しない |
| 各要件が**初期状態と到達すべき状態**を述べることを要求する | **可。** 自己完結する |

§2(1) の結論（「落ちたのは実装だけ」）を書くには、**後者の型でなければ役に立たない。**

この基準は未決の問い1（分析と定義を分けるか）にも答えを与える ──
**自己完結した検査が2つ立つまでは分けない。層の数 = 検査の数。**

## 4. 戻り距離 ── 診断が決める

**ループをどこから始めるかは、事前の方針ではなく診断の関数である。**

あるモジュールがコーディングを終えた時点で不具合があると判定できるとき、それが
コードの問題か設計の問題かは分かる。その判定は機械的でよい。**そこからどこまで戻るかを
決める。** これが変更 5 の「ウォーターフォールだがループが回る」の実体である。

### 戻り先は §3 の系として従属する

自己完結した検査は、**自分がどの層のものかを名乗る。** だから診断表は新しい設計物ではなく、
**検査表の裏返し**になる。

| 落ちた検査 | 示すもの | 戻る層 |
|---|---|---|
| VERIFY（FAIL_TO_PASS） | 実装がテストを満たさない | 実装 |
| VERIFY（PASS_TO_PASS） | 実装が既存を壊した | 実装 |
| 依存グラフ（孤児・循環） | モジュール構成の誤り | 設計 |
| 要件被覆（初期状態・到達可能性） | 定義の穴 | 定義 |
| **（無い）** | **テストが設計を誤って写した** | **テスト** |

### 診断は2クラスではなく3クラス

3つめは「テストが間違っている」であり、**この系で既に起きている。**

> run 8 の S5 で、`return storage.getItem(KEY)` という**完全に正しい実装が6回書かれて
> 6回落ちた。** テストが自前で書いた偽 Storage が `""` を `null` に潰していたため。

このとき「テストが落ちた ⇒ コードの問題 ⇒ 実装に戻る」と診断すると、**状態機械は
止まらない。実測で6周した。** S3（期待値リテラルの括弧落ち）と S4（存在しないマッチャ）
も同じ型で、**run 8 の未解決の失敗3件は全部このクラス**である。
そして**いまの系にこれを判定する検査が無い**（表の最後の行）。

### これが変更 2 の必要条件になる

「テストが設計と矛盾する」と言うには、**設計が比較可能な形で存在しなければならない。**
設計が `tasks.json` の中に暗黙にある限り、テストと突き合わせる相手がいないので、
3つめのクラスは永久に「コードの問題」に誤分類される。

> **戻り距離の機構は、モジュール設計を独立した機械可読な層にすることを要求する。**
> 解像度の議論より強い根拠である ── **無いと状態機械が止まらない。**

なお `contracts.provides` / `requires` とスタブ生成器が、既にこの型の部品を半分持っている
（契約から決定的にコードを組んでいる）。ここは新しい道具ではなく、**やりかけのものの延長**。

## 5. 無効化の伝播 ── 誰も担当していない

診断は**どこへ戻るか**を決めるが、**何が陳腐化するか**は決めない。

モジュール単位でインクリメンタルに作るなら、S7 の不具合で設計層に戻って構成を変えたとき、
**既に緑で凍結されている S2 のテストはどうなるか。**

run 8 で具体化すると、S5（storage の読み出し）は S2 の storage モジュールに依存している。
S5 の診断で設計に戻って境界を引き直せば、**S2 の緑は意味を失っているのに緑のまま残る。**

部分的な前例がある ── **PASS_TO_PASS は「緑を壊していないこと」を既に要求している。**
つまり「緑を保つ」機構はある。**無いのは「緑を取り消す」機構である。**

依存グラフ（変更 2 の出力）があれば機械的に出るはずだが、**いま誰の担当でもない。**
状態機械（変更 4）の設計に入れる必要がある。

## 6. テストを誰が書くか

変更 3 を進めると、役の構成が動く。ここには測定済みのデータがある。

| ローカル 9B は | 結果 |
|---|---|
| **実装を書く** | S1・S2・S4 を**1回目で緑**。S1 は12テスト、S2 は17テスト |
| **テストを書く** | run 8 の未解決の失敗は**3件とも TEST_WRITE** |

```
S3   期待値リテラルから { } が落ちた
S4   expect(...).deepEquals(...)       存在しないマッチャ
S5   モックの getItem が "" を null に潰す / vi.mocked(...).mockClear が無い
```

**どれも判断の失敗ではなく転写の失敗である。**

> **弱いモデルは、テストに沿って実装するほうが、テストを書くより得意である。**
> 「テストが仕様」であるなら、仕様を弱いモデルに書かせる理由が無い。

| 案 | テストを書くのは | 代価 |
|---|---|---|
| **A** 現状維持 | ソルバー（弱いモデル） | 3件の型が繰り返される。凍結後は直せない |
| **B** 強いモデルに移す | プランナー側 / 専任の役 | 呼び出しが増える。**BOOTSTRAP 1-1 の分離が緩む**（基準の作者がテストも書く） |
| **C** 機械が組み立てる | ランナー | スタブ生成で部分実証済み。**ただしテストは判断を含む** |

**見立て: C の範囲を測るのが一番安い。** `given` と `then` が具体値を持つなら
`expect(f(具体値)).toBe(具体値)` への変換に判断は要らない。L8 が受け入れ条件に具体値を
要求しているのは、まさにそれを可能にする形である。

## 7. 1つのプログラムにする ── 停止点を失わないこと

**いまの動詞の分離は意図的である。**

> `plan propose` は費用を使い、`plan apply` は**ループが測られる対象**を書き換える。
> 提案を読んでからどちらを起こすかを決められなければならない。
> `plan apply` は**基準が草案である最後の瞬間**で、この系で最も重要な境界である。

**解は「1プログラム・1状態機械・明示的な停止点」**であって、「1コマンドで無停止」ではない。

```
いま:   次に打つ動詞を人間が覚えている        ← ループは操作者の中
提案:   次の段を状態機械が持ち、停止点で止まる  ← ループは機械の中
```

**停止点はデータになる**（「人間の判断待ち」という状態）。そして §2(1) の結論を書くには、
**どの層が何を出したかが記録されていなければならない** ── それができるのはこの変更からである。

副産物として、未解決の欠陥を1つ直す ──

> **位相単位の再実行が無い。** run 8 の S1 は RED_GATE を 12/12 で抜けて IMPL の文脈長で
> 落ち、復旧手段は `reset` だけだった ── **通ったばかりのテストを捨てて引き直す。**

## 8. ウォーターフォールとの違い

層が順に流れる点はウォーターフォールだが、**戻れる点が違う。**

ウォーターフォールの弱点は「欠陥の発見が遅く、遅いほど高い」こと。この設計の答えは:

> **各層の出力は、次の層が始まる前に検査できる。**

実証がある ── run 7 の「遊べない」は **critic が計画だけから、要件も実装も見ずに導出した**
（不動点であることを `8760h -> resource=0.0` の算術つきで示した）。**実装を1時間焼く前に
分かる欠陥だった。**

層を増やすことは「手戻りの距離が伸びる」危険を持つ。**それを打ち消すのが §3（各層に
自己完結した検査がある）と §4（戻り距離が診断から出る）**である。

## 9. 捨てるもの・壊れるもの

| | |
|---|---|
| **`tasks.json` の形式** | 8 run ぶんの蓄積がある。上流に層が増えると、その出力と計画の関係を定義し直す必要がある |
| **リンタ L1〜L15** | 全部 `tasks.json` に対する規則。新しい層には**自前の規則が無い** |
| **既存 run との比較可能性** | run 1〜8 は「要件 → 計画 → 実装」で測った。層が増えると run 9 以降と直接比較できない |
| **呼び出し回数** | TypeScript のブートストラップは**1試行28分**だった。上流に2〜3層増えると1周が数時間になる |
| **「機械が自分について嘘をつく」場所が増える** | run 8 の S1 は13回止まり12回がこれだった（言語・文脈長・エラーの可読性・失敗の報告）。層が増えるとこの面積も増える |

最後の1行だけは、完璧前提を置いても消えない ── **変更 4 はこの面積を減らす唯一の変更**
である（状態が操作者の記憶からデータに移るため）。

## 10. 推奨する順序

解像度と戻り距離から出る順序。

| | やること | なぜその位置か |
|---|---|---|
| **1** | 変更 4（1プログラム・状態機械・停止点はデータ） | **層の帰属を記録できるのはこれが入ってから。** §2(1) の結論は、どの層が何を出したかが残っていないと書けない |
| **2** | 変更 2（モジュール設計） | 検査が**自己完結する**（依存グラフ・孤児・循環は下流を見ない）。§3 の型を最初に実証でき、§4 の3クラス診断の前提になる |
| **3** | 変更 1（要件の層） | 自己完結する検査を作るのが提案中で最も難しい。2 でパターンが確立してから |
| **－** | 変更 3 | 上の3つと**直交**する。いつでも独立に測れる |

**測定上の制約:** 層の追加（変更 1・2）と裁量の縮小（変更 3）を**同じ run に入れない。**
入れると run 9 の結果がどちらで動いたのか分からない。

**run 8 をリセットしない。** S3・S4・S5 は「弱いモデルがテストを書いて失敗した、内容の
分かっている3件」で、§4 の3クラス診断と §6 の C を**新しい run を焼かずに検証できる
対照群**である。

## 11. 未決の問い

1. **要件分析と要件定義を分けるか。** §3 の基準に従えば「自己完結した検査が2つ立つなら分ける」
2. **各層の検査の具体形。** §3 の基準を満たす候補を挙げ、満たさないものを落とす
3. **テストを誰が書くか。** A（現状）／B（強いモデル）／C（機械）── §6
4. **モジュール設計は計画と別の層か。** いまの `tasks.json` は暗黙に両方やっている ──
   何が存在するかと、どの順で作るか
5. **「テストが設計と矛盾する」を判定する検査の形**（§4 の表の空いた行）
6. **無効化の伝播を誰が決めるか**（§5）── 設計層に戻ったとき、どの下流の凍結が解かれるか
7. **run 9 を新しい形で回すか**、run 8 を終わらせてからにするか（run 8 は S1〜S4 緑、S5 で停止中）

## 付録 ── いまの形との対応

```
いま:
  REQUIREMENTS.md ──→ plan bootstrap ──→ critique ──→ plan apply ──→ run --all
  （人間が書く）      （計画＝モジュール    （欠陥を指摘）  （基準確定）   （ステップごとに
                       構成＋順序）                                      TEST_WRITE→STUB→
                                                                        RED_GATE→FREEZE→
                                                                        IMPL⇄VERIFY）

提案:
  要件分析 ──→ 要件定義 ──→ モジュール設計 ──→ テスト ──→ 実装
    ?           ?            依存グラフ          ?          VERIFY
    └─ 各層に自己完結した検査が要る（§3）        └─ 誰が書く（§6）

  落ちた検査が戻る層を名乗る（§4）。戻ったとき何が陳腐化するかは別途（§5）。
  全体が1つのプログラムで、停止点を持つ状態機械として回る（§7）。
```
