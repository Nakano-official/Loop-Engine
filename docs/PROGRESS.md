    ブリーフが 16,400 トークンになって 9B の文脈（13,824）に入らなかった。→ 組み立ての例のうち定義の例と

  - **見つかった穴: 通しのやり直しも、設計への戻りも、緑のモジュールを捨てて全部作り直している。**
    エンジンの直しは組み立てにしか効かないのに、5つの緑を 9B にもう一度作らせた。→ 次の 1

- **迷路の出力は、テストは全部通ったのに「何か分からない」ものだった**（最初の画面は壁一面、操作説明が無い、
  灰色ばかり、分かれ道の無い1本道）。どの関門もこれを見ておらず、人が開いて気づいた。
  ループが閉じているのは内側（実装 ⇄ テスト）だけで、外側（できたもの ⇄ 目的）は人が回していた。

**次:**（DESIGN §4〜§6 の順。実装の前に、形式と役を決める）

1. **要求分析の層**: 分析の形式（概念ファイル `concepts.json` と要件、FORMATS）、分析役、definer のブリーフを「要求から」ではなく
   「要件と概念ファイルから」に、覆いの関門。名前を要求・要件に直す
3. **自己完結の関門**: 文書の中の文章による参照（「D1で定めた」「相当」「上記」）を指摘にする
3. **評価の段**: 箱の中で本物のブラウザ（WebGL つき）を exec として動かし、証拠（画面・決まった操作の結果）を

4. **続きから**: 緑になったモジュールに指紋（自分の契約・doc・例、依存先をたどった全部、使う型・エラー・共有の値、

   受け入れる。作り直すのは指紋が変わったものとその上だけ。改良の輪を回す前提
5. **改良の輪**: 評価の指摘 → 悪い段 → 作り直し → 評価、止まる条件まで
6. 何回か通して率を測る仕組み（同じ要求で何回通るか。DECISIONS 未決 5 の材料）
