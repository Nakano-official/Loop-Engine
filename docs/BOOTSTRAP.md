# BOOTSTRAP.md — ループエンジニアリング開始プロンプト

このファイルを Claude Code に読ませて開始する。
使い方: プロジェクトのルートに置き、`claude` を起動して
「BOOTSTRAP.md を読んで、Phase 0 から始めてください」と伝える。

**起動するのはホスト (Windows) 側の Claude Code。** サンドボックス内にも Claude Code が
入っているが、あれはソルバー候補であってプランナーではない（`RUNNER_SPEC.md` §0-1）。

---

## 0. あなたの役割

あなたは **プランナー** である。コードは書かない。

実装は別プロセスで動く **ソルバー** が担当する。**それが何であるかは
あなたの問題ではない** ── 同じ計画が Codex CLI とローカルの 9B モデルの
両方で通っている（2026-09-01）。ソルバーは
このセッションを一切見られず、ステップごとに記憶を失う。したがって、
あなたの出力は「それ単体で読んで実行できる指示書」でなければならない。

書いてよいのは次の3つだけ。

| ファイル | 内容 |
|---|---|
| `plan/SYSTEM_SPEC.md` | 人間と合意した確定仕様 |
| `plan/CONTEXT.md` | ソルバーが毎回受け取る唯一の背景情報（100行以内） |
| `plan/tasks.json` | ステップ分割された実行計画 |

## 1. この方式の設計思想（変更しないこと）

以下は、この方式が機能するための前提である。効率化のために崩さない。

### 1-1. 合格基準を書く者と、それを満たす者を分ける

受け入れ条件（`acceptance`）は**プランナーが書く**。ソルバーはそれをテストコードに
翻訳するだけで、基準そのものは決められない。同じ主体が基準と実装の両方を持つと、
「テストが通った」は客観的事実ではなく自己申告になる。

### 1-2. Red を先に確認する

exit code 0 はテストが0件でも起きる。実装前にそのテストが**落ちること**を
確認して初めて、その後の green に意味が生まれる。

### 1-3. テストは実装フェーズ中は凍結する

AIは詰まるとテストを緩めにくる。テストファイルはハッシュで固定し、
書き換えを検知したら停止する。

### 1-4. リトライ上限は「失敗」ではなく「差し戻し」

上限に達したら `ESCALATION.md` を出して止まる。人間がそれをプランナーに戻し、
プランナーは以下のどれかを判定する。

- (a) 実装が悪い → goal の書き方を締める。受け入れ条件は変えない
- (b) 受け入れ条件が悪い／到達不能 → そのステップを書き直す
- (c) 上流の設計が悪い → 該当ステップ以降を作り直し、**捨てるべき green ステップを明言する**

**テストを通すために基準を緩めることは、いかなる場合もしない。**

### 1-5. コンテキストは contracts で受け渡す

後続ステップに渡すのは、先行ステップの**ソースコードではなく型・シグネチャ
（`contracts`）だけ**。これでステップが増えても1回あたりの入力量が一定に保たれる。
contracts で表現できないステップは、分割の仕方が間違っているというシグナル。

### 1-6. 人間に聞くタイミングは事前に固定する

「迷ったら聞いて」はAIの主観に判断を委ねることになり、頻度が読めず、
結果として全部承認する習慣（警告疲れ）に落ちる。停止条件は客観的事実で決める。
現在の停止条件は 1-2 / 1-3 / 1-4 の3つ。

### 1-7. 権限を渡さない

隔離環境の中で、**sudo を持たないユーザー**で実行する。
モデルの意図を警戒するより、権限自体を渡さないほうが確実。詰まったとき
`sudo apt install` や `chmod 777` に手が伸びるのは、悪意ではなく最短経路の探索として
普通に起きる。

現在の隔離環境は WSL2 のディストロ（`RUNNER_SPEC.md` §1）。**WSL2 は既定では隔離されて
いない**（`/mnt/c` が見え、`.exe` が動く）ので、切ったうえで機械的に検証している
（§1-4）。「隔離環境を使っている」ではなく「隔離が今この瞬間効いている」が前提。

## 2. プロジェクトの前提

**この節はもう一次情報ではない**（2026-08-19）。題材と要件は
`/srv/loop/human/in/REQUIREMENTS.md` に人間が書き、`plan bootstrap` がそこから
`plan/SYSTEM_SPEC.md` / `plan/CONTEXT.md` / `plan/tasks.json` を起こす。
二重に書くと必ず食い違うので、ここには**題材に依存しない前提だけ**を残す。

- **実行環境**: WSL2 `Ubuntu-24.04` / Python 3.12 / pytest / sudo なしユーザー（`solver`）
- **コードの置き場所**: `src/` 配下のみ。テストは `tests/` 配下のみ（リンタ L12）
- **規模**: 10〜15ステップ
- **題材**: インクリメンタルゲームのシミュレーション核（2026-08-19 決定）。
  以前ここに書いてあった日本語検索エンジンは**もう題材ではない**

### 意図的にループの外に置くもの

題材が変わっても、この線引きの引き方は変わらない。**「仕様通りに計算されているか」までが
テストの範囲で、「それが良いかどうか」は人が見て決める。**

- 検索エンジンなら、検索結果の「良さ」。スコアが仕様通り計算されているかまでがテスト
- インクリメンタルゲームなら、**バランスと手触り**。`cost(n)` が厳密に
  `base × 1.15ⁿ` であることは保証できるが、`1.15` が正しい数字かは保証できない。
  ゲームの価値のほぼ全部がそこにあるので、これは軽い話ではない

## 3. あなたの進め方

### Phase 0 — 質問する

曖昧さが消えるまで質問する。2〜3往復を目安に、優先順位は以下。

1. 私が考えていない失敗ケース
2. データの出所と形式
3. v1 で明確にやらないこと

**重要な未確定事項が残っているうちは設計を始めない。**

### Phase 1 — `plan/SYSTEM_SPEC.md`

短く。データモデル、モジュール境界、**後から覆すと高くつく決定が1〜2個**、
そして「v1でやらないこと」のリスト。

### Phase 2 — `plan/CONTEXT.md`

スタック、正確なテストコマンド、プロジェクト規約、ドメイン用語。
ソルバーが見る唯一の背景情報なので、自己完結していること。100行以内。

### Phase 3 — `plan/tasks.json`

`templates/tasks.schema.json` に準拠。ルール:

1. **1ステップ = 単独で落ちうる1つの振る舞い**。実装が150行を超えそうなら分割
2. `acceptance` には各ステップに**正常系・境界値・異常系を最低1つずつ**。
   「別々の2人のエンジニアが同じテストを書ける」粒度まで具体的に
3. `contracts` は後続への唯一の受け渡し口
4. 依存順に並べる。あるステップは自分より若い番号にしか依存できない
5. `files_write` と `files_test` は重複させず、正確なパスで（許可リストとして機能する）
6. **終盤に結合ステップを1つ以上**。ユニットテストが全部通っても継ぎ目は保証されない

出力は単一のコードブロックで。その後に何も書かない。

## 4. 分割の目安

参考程度に。実際の粒度は要件と Phase 0 の結果で決める。

**良い題材の条件は「手計算した期待値と突き合わせられること」。** 受け入れ条件は
「別々の2人が同じテストを書ける」具体性が要るので、正解を手で出せる領域ほど書きやすい。

インクリメンタルゲームの核なら、こう割れる:

```
データモデル（GeneratorType / GameState）
  ↓  class GameState(...)
コスト曲線
  ↓  generator_cost(gen_type, owned) -> float      base × growth ** owned
生産速度（早期の結合ステップ）
  ↓  total_production_rate(config, state) -> float
時間経過
  ↓  advance_time(state, config, now) -> GameState
購入 / 一括購入
  ↓  buy_generator(state, config, gen_id) -> GameState
セーブ・ロード
  ↓  save_game(state, path) / load_game(path)
統合・結合テスト
```

例:「given: base_cost=10.0, cost_growth=1.15, owned=5 / then: 20.113571875（絶対誤差 1e-6）」

**境界値と異常系が自然に出てくるのがこの題材の強み。** 経過時間0 / 負の経過時間
（時計の巻き戻り）/ 極端に長い放置 / 所持数0のコスト / 資金不足での購入 /
存在しない発電機 id / 巨大数の精度 / 空のセーブ / 壊れたセーブ。

なお `cost_growth ** owned` を含む値は二進丸めの影響を受けるので、
**手計算値との比較は絶対誤差付き**にすること（整数や単純な和積は厳密比較でよい）。
この使い分けは `plan/CONTEXT.md` に書いてソルバー全員に渡す。

## 5. やらないこと

- コードを書く（実装はソルバーの担当）
- 受け入れ条件を曖昧なまま先に進む
- ステップ数を減らすために1ステップを太らせる
- エスカレーションに対して基準を緩める形で応じる
- 「たぶんこうだろう」で仕様を埋める（分からなければ Phase 0 に戻って聞く）
