## 1. 全体

| ファイル | 段 | 中身 |
|---|---|---|
| `definition.json` | 要件定義 | **外部インターフェース**（型・エラー・関数）、定義項目とその例、シェルの務め |
| `design.json` | モジュール設計 | 型・エラー・共有の値、モジュール（契約・依存・例）、組み立て、シェルの呼び先 |

どちらも**言語に依らない**。対象言語は `design.json` の `target` だけが持ち、言語ごとの差はアダプタ（REDESIGN §5）が埋める。

## 2. 型

| 書き方 | 意味 | 値の書き方（JSON） |
|---|---|---|
| `int` | 整数。**±2^53 の範囲**（JavaScript が正確に持てる範囲） | 数 |
| `float` | 倍精度浮動小数 | 数 |
| `string` / `bool` | 文字列 / 真偽 | 文字列 / `true` `false` |
| `list<T>` | 順序のある並び | 配列 |
| `map<string,T>` | 文字列をキーにした対応。**順序は無い** | オブジェクト |
| `optional<T>` | 無いかもしれない値 | `null` か値 |
| 名前（`GameState` など） | `types` で宣言した record か enum | record はフィールドを**過不足なく**持つオブジェクト、enum は文字列 |

```json
"types": {
  "GameState": {"record": [
    {"name": "resource", "type": "float"},
    {"name": "owned", "type": "map<string,int>"}
  ]},
  "Phase": {"enum": ["playing", "paused"]}
}
```

- record のフィールドは**並びで**宣言する。引数を位置で渡す言語があるので、順序は意味を持つ
- **順序が意味を持つものは `list` にする。** `map` の並びは言語ごとに違う（§8-4）
- **v1 に無いもの:** クラスとメソッド、関数を値として渡すこと（コールバック・クロージャ）、
  その場での書き換え、文字列以外をキーにした map。どれも言語ごとの差が大きく、
  関数と値だけなら全言語で同じ形に書ける。状態は値として受け取り、新しい値として返す

### エラー

```json
"errors": {"NotEnough": "資源が値段に足りない"}
```

名前と説明だけを持つ。関数は `raises` で投げうるエラーを宣言する。
言語への写し方（例外クラス、`Result`、Go のエラー値、C の戻り値）はアダプタが決める。

## 3. 契約

```json
"buy": {
  "params": [{"name": "state", "type": "GameState"}, {"name": "catalog", "type": "list<GeneratorSpec>"}, {"name": "name", "type": "string"}],
  "returns": "GameState",
  "raises": ["NotEnough", "UnknownGenerator"],
  "doc": "catalog.find_spec で spec を得る。economy.current_cost(spec, 所有数) を値段とし、足りなければ NotEnough。……"
}
```

- **`doc` は設計では必須。** その関数が**どう**するか ── どの依存先のどの関数をどう組み合わせるか、
  どの式で計算するか ── を書く。設計の関門は `doc` の無い関数を拒む
- 定義の外部インターフェースでは `doc` は任意（定義は項目の `statement` で「何を」を言う）。
  組み立ての契約を外部インターフェースと照合するとき、`doc` は比べない ── 定義は「何を」、設計は「どう」
- 2026-10-10、本物の solver で放置ゲームを通したとき、組み立ての `load`（読み戻して今の時刻まで進める）
  が3回とも作れなかった。その組み合わせ方は、例にも、solver が読むものにも、どこにも書かれていなかった。
  これが `doc` を必須にした理由である

- 名前は小文字とアンダースコア（`snake_case`）。**アダプタは設計の名前をそのまま使う**
  （Python・TypeScript とも）。正規形に戻すときに訳し戻しが要らないからである。その言語の
  予約語に当たる名前にだけ `_` を付ける（Python の `class` → `class_`、TypeScript の `delete` → `delete_`）。
  record のフィールドは、Python では元の名前をメタデータに持ち、正規形では元の名前に戻す
- **関数名はモジュールの中でだけ一意。** 例の中で依存先の関数を呼ぶときは `rules.buy` のように
  モジュール名を付ける（§8-2）

## 4. 例

例は**データ**であり、コードではない。

```json
{
  "id": "M4.E5",
  "from": "D3",
  "steps": [
    {"let": "s", "value": {"resource": 15.0, "owned": {}, "last_update": 0.0}, "type": "GameState"},
    {"let": "b", "call": "buy", "args": {"state": {"$": "s"}, "catalog": {"$": "CATALOG"}, "name": "cursor"}}
  ],
  "then": {"observe": ["s"], "equals": [{"resource": 15.0, "owned": {}, "last_update": 0.0}]}
}
```

| 項目 | 意味 |
|---|---|
| `id` | `<定義項目またはモジュール>.E<番号>`。記録・トレース・帰責はこの ID で行う |
| `steps` | 順に実行する。`call` は関数を呼んで結果を `let` の名前で持つ。`value` は型つきの値をそのまま持つ |
| `args` | **引数名で**渡す。値は直書きか、`{"$": "名前"}` で前の段の結果や共有の値を指す |
| `then.observe` / `equals` | 最後に、名前の付いた値を期待値と比べる。**比べるのは1回**（複数の値をまとめて比べてよい） |
| `then.raises` | **最後の段が**そのエラーを投げること。それより前の段は成功しなければならない |
| `tol` | 浮動小数の許容誤差。省略時は相対 1e-9・絶対 1e-12 |
| `from` | どの定義項目から起こしたか（任意。トレース用） |

- **入力を変えないこと**は、呼んだあとで入力の名前を観測すれば書ける（`D2.E2`、`M4.E5`）
- 例の中で呼べるのは、そのモジュールの関数と、`depends_on` に書いたモジュールの関数だけ

### 共有の値（fixtures）

```json
"fixtures": {"CATALOG": {"type": "list<GeneratorSpec>", "value": [ ... ]}}
```

`design.json` に置き、例から `{"$": "CATALOG"}` で指す。名前は大文字。例の `let` で同じ名前を使ってはならない。

## 5. モジュール

```json
{
  "id": "M4", "name": "rules", "kind": "pure",
  "depends_on": ["M1", "M2"],
  "functions": { ... },
  "examples": [ ... ]
}
```

| `kind` | 意味 |
|---|---|
| `pure` | 値を受け取り、値を返す。I/O も時計も持たない |
| `assembly` | 組み立て。**ちょうど1つ。** 契約は定義の外部インターフェースと**完全に同じ**。例は定義の例そのもの（機械が写す。`examples` には足したいものだけを書く） |
| `support` | テスト側の道具（偽物など）。例を持ち、使われる前に自分の赤→緑を通す（REDESIGN §4）。放置ゲームでは要らなかった |

作る順序は `depends_on` から機械が求める（トポロジカル順）。`design.json` には書かない。

## 6. シェル

**I/O・時計・画面は、シェルにしか無い。** シェルは外部インターフェースの関数を呼び、結果を
プラットフォームとやり取りするだけの薄い層で、例では確かめられない。

| | 持つもの |
|---|---|
| `definition.json` の `shell` | `platform`（`browser-dom` か `browser-3d`。REDESIGN §1）と、務めの箇条書き（散文） |
| `design.json` の `shell` | `calls`: 組み立てモジュールの ID |

シェルの中身は人間のレビュー（REDESIGN §4 の最後の段）で確かめる。

**出力は1つの HTML ファイル**（REDESIGN §1 の目的）。作業場のモジュールとシェルを1つにまとめ、
開けば画面が出る形にする。シェルはアプリごとに書かず、**プラットフォームごとに機械側が用意する汎用の
シェル**にする方針で、アプリは画面の記述（データ）を返す。画面の記述の形は未決（REDESIGN §10）。

## 7. 出口の関門

`engine/artifacts.py`（`check_definition` / `check_design`）。どの指摘も、悪い段（要件定義かモジュール設計か）と
場所を持ち、そのまま帰責（REDESIGN §4）に使える。設計の関門は、関門を通らなかった定義に対しては判定しない。
両方向のテスト 26 件（放置ゲームは通り、壊した 24 通りはどれも正しい段・正しい場所で拒まれる）。

### 定義の関門

| 検査 | 落ちたら |
|---|---|
| ID が一意。例の ID が自分の項目の下にある | 要件定義 |
| 例の無い定義項目が無い。例の無いインターフェース関数が無い | 要件定義 |
| 例の引数名が契約と過不足なく一致し、値が型に合う | 要件定義 |
| 参照（`$`）が前の段か共有の値を指す | 要件定義 |
| `raises` が、最後の段の関数が宣言したエラー | 要件定義 |

### 設計の関門

| 検査 | 落ちたら |
|---|---|
| 定義の型を**同じ形で**持ち、定義のエラーを全部持つ | モジュール設計 |
| 依存先が存在し、循環しない | モジュール設計 |
| 組み立てがちょうど1つで、契約が外部インターフェースと完全に同じ | モジュール設計 |
| シェルの呼び先が組み立て。全モジュールが組み立てから依存をたどって届く | モジュール設計 |
| 全関数に例がある（組み立ては定義の例で満たす） | モジュール設計 |
| 全関数に `doc` がある。契約に知らない欄が無い | モジュール設計 |
| 例が呼ぶのは、自分か依存先の関数だけ | モジュール設計 |
| 定義の例が、組み立ての契約の上でそのまま成り立つ形をしている | モジュール設計 |
| 共有の値が型に合う | モジュール設計 |

試作のあとで足した検査:

| 検査 | 落ちたら |
|---|---|
| 同じ関数・同じ入力（1段の例）に違う期待値（矛盾） | その段 |
| 参照（`$`）の型が引数の型に合う。T は optional<T> に渡してよい | その段 |
| 定義のプラットフォームが `browser-dom` か `browser-3d`（REDESIGN §1） | 要件定義 |
| 設計の対象言語にアダプタがあり、プラットフォームが定義と同じ | モジュール設計 |
| 名前の形（関数・フィールド・モジュールは snake_case、型・エラーは CapWords、共有の値は UPPER_CASE） | その段 |
| map のキーに `$` だけを使わない（参照と区別できない） | その段 |

## 8. 試して分かったこと

### 8-1. テストは機械が生成できる

試作は、手で書いたテストを1本も使わずに、**例 46 件を汎用の実行器で参考実装に当てた。**
例は全部データ（呼ぶ関数・引数名つきの値・観測する名前・期待値）なので、テストのコードは
「型に合わせて値を作り、関数を呼び、比べる」の書き写しにしかならない。
アダプタが言語ごとにこの書き写しを生成できる。

**だからテストは機械が生成する**（REDESIGN §10 の決定 2）。v1 の形（関数と値だけ）の範囲では、
テストを書くことに判断の余地が残らない。tester（Claude）は支援モジュールの中身だけを書く。

### 8-2. 関数名はモジュールの中でだけ一意にする

組み立ての `buy(state, name)` と、依存先の `buy(state, catalog, name)` が衝突した。
試作の関門が最初の実行で見つけた。モジュール名で修飾して呼ぶ形にした。
**C には名前空間が無い**ので、C のアダプタは記号にモジュール名を前置する。

### 8-3. 丸めは言語ごとに違う

`50.625` を小数2桁にすると、**Python は `"50.62"`、Node は `"50.63"`**（実測）。
Python は最近接偶数に、JavaScript の `toFixed` は切り上げ側に丸める。

- 数を文字列にする関数は、**丸め方を設計の文で宣言する**
- 期待値は宣言した丸め方で計算する。設計者が自分の言語の既定で計算すると、別の言語で書いたときに落ちる
- 境目（`.xx5`）の例は、その丸め方を固定するために**わざと置く**価値がある

放置ゲームの例は境目を避けている（`33.75`、`100.00`）。避けるか固定するかは設計が選ぶ。

### 8-4. 順序が要るものは list

画面の行は cursor、grandma の順に出したい。カタログを `map` にすると並びが言語ごとに変わるので、
`list<GeneratorSpec>` にした。

### 8-5. 文字列の正確な形は、往復と読み込みで固定する

保存の `encode` の出力は例で固定していない。`15.0` を `15` と書くか `15.0` と書くかが言語で違うからである。
代わりに、**往復（`decode(encode(s)) == s`）と、決まった文字列の `decode`** で、意味のある部分だけを固定した。

### 8-6. run 7・run 8 の組み立ての穴は、関門で止まる

| | 何が欠けていたか | この形では |
|---|---|---|
| run 7 | 最初の資源を得る経路が、どのモジュールにも属していなかった | 定義の項目（`D2` クリック）になり、組み立ての契約に入る。例の無い関数は関門で落ちる |
| run 8 S1 | `app.ts` が作られ、テストされ、出荷物から呼ばれなかった | シェルの呼び先は組み立て。組み立てから届かないモジュールは関門で落ちる |

## 10. 記録

比較関数が書き出す、判定の元になるもの（REDESIGN §4）。**どの言語でも同じ形**で、
`$LOOP_RECORD_DIR/records.jsonl` に1行1件、書くたびに flush する。

```json
{"t": "start", "id": "M2.E1"}
{"t": "check", "id": "M2.E1", "ok": true,  "expected": [33.75], "actual": [33.75]}
{"t": "check", "id": "M1.E3", "ok": false, "expected": {"raises": "UnknownGenerator"}, "actual": {"returned": {"name": "x"}}}
```

| 形 | 意味 |
|---|---|
| `start` のあと同じ ID の `check` | 比べた。`ok` が結果 |
| `start` だけ | 比べる前に落ちた（例外・クラッシュ）。理由はテストフレームワークの出力から読む |
| どちらも無い | そのテストは走らなかった（ビルドできない、など） |

- `expected` / `actual` は §2 の正規形。値の例は `then.equals` と同じく**観測する値の並び**、
  エラーの例は `{"raises": 名前}` と、実際に起きたこと（`{"raises": 名前}` か `{"returned": 値}`）
- 期待値はテストに書かない。比較関数が `LOOP_EXAMPLES`（窓口が用意する例のファイル）から読む
- Python の実装: `adapters/python/loopcheck.py`

### 例のファイル

アダプタは作業場の直下に `examples.json` を置き、`exec-run` がそれを `LOOP_EXAMPLES` として渡す
（全言語共通の決まり）。中身は設計の全部の例で、組み立てモジュールには定義の例が入る。
各段には、言語に依らない中核（`adapters/design.py` の `examples_file()`）が次を書き足す:

| 書き足すもの | 用途 |
|---|---|
| `module` / `function` | `rules.buy` のような修飾を解いた、呼ぶ先 |
| `arg_types` | 各引数を、どの型として組み立てるか |
| `returns` | 戻り値の型 |

生成されたテストは、入力も期待値も直書きしない。入力は段と引数名で比較関数に頼み
（Python では `loopcheck.arg(ex, 段, 名前)`）、型どおりに組み立てられた値を受け取る。
前の段の結果を指す参照（`$`）だけは、テストの中の変数になる。
