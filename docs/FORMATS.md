## 1. 全体

| ファイル | 段 | 中身 |
|---|---|---|
| `definition.json` | 要件定義 | **何を作るか**（`summary`）、**外部インターフェース**（型・エラー・関数）、定義項目とその例（項目は確かめている概念ファイルの番号を `concepts` 欄に持つ）、プラットフォーム。要求から作るときは3者で書き分ける: 何を作るかを definer、プラットフォームの型と関数を機械、例を tester（§12） |
| `design.json` | モジュール設計 | 型・エラー・共有の値、モジュール（契約・依存・例）、組み立て、シェルの呼び先 |
| `concepts.json` | 要求分析 | **概念ファイル**: 要求の原文、概念とその性質と反例、必要なこと（要件）、範囲外、任意の背景（§11） |

いずれも**言語に依らない**。対象言語は `design.json` の `target` だけが持ち、言語ごとの差はアダプタ（DESIGN §7）が埋める。

## 2. 型

| 書き方 | 意味 | 値の書き方（JSON） |
|---|---|---|
| `int` | 整数。**±2^53 の範囲**（JavaScript が正確に持てる範囲） | 数 |
| `float` | 倍精度浮動小数 | 数 |
| `string` / `bool` | 文字列 / 真偽 | 文字列 / `true` `false` |
| `list<T>` | 順序のある並び | 配列 |
| `map<string,T>` | 文字列をキーにした対応。**順序は無い** | オブジェクト |
| `optional<T>` | 無いかもしれない値 | `null` か値 |
| 名前（`GameState` など） | `types` で宣言した record か enum | record はフィールドを**過不足なく**持つオブジェクト、enum は文字列 |

```json
"types": {
  "GameState": {"record": [
    {"name": "resource", "type": "float"},
    {"name": "owned", "type": "map<string,int>"}
  ]},
  "Phase": {"enum": ["playing", "paused"]}
}
```

- record のフィールドは**並びで**宣言する。引数を位置で渡す言語があるので、順序は意味を持つ
- **順序が意味を持つものは `list` にする。** `map` の並びは言語ごとに違う（§8-4）
- **v1 に無いもの:** クラスとメソッド、関数を値として渡すこと（コールバック・クロージャ）、
  その場での書き換え、文字列以外をキーにした map。どれも言語ごとの差が大きく、
  関数と値だけなら全言語で同じ形に書ける。状態は値として受け取り、新しい値として返す

### エラー

```json
"errors": {"NotEnough": "資源が値段に足りない"}
```

名前と説明だけを持つ。関数は `raises` で投げうるエラーを宣言する。
言語への写し方（例外クラス、`Result`、Go のエラー値、C の戻り値）はアダプタが決める。

## 3. 契約

```json
"buy": {
  "params": [{"name": "state", "type": "GameState"}, {"name": "catalog", "type": "list<GeneratorSpec>"}, {"name": "name", "type": "string"}],
  "returns": "GameState",
  "raises": ["NotEnough", "UnknownGenerator"],
  "doc": "catalog.find_spec で spec を得る。economy.current_cost(spec, 所有数) を値段とし、足りなければ NotEnough。……"
}
```

- **`doc` は設計では必須。** その関数が**どう**するか ── どの依存先のどの関数をどう組み合わせるか、
  どの式で計算するか ── を書く。設計の関門は `doc` の無い関数を拒む
- 定義の外部インターフェースでは `doc` は任意（定義は項目の `statement` で「何を」を言う）。
  組み立ての契約を外部インターフェースと照合するとき、`doc` は比べない ── 定義は「何を」、設計は「どう」
- 2026-10-10、本物の solver で放置ゲームを通したとき、組み立ての `load`（読み戻して今の時刻まで進める）
  が3回とも作れなかった。その組み合わせ方は、例にも、solver が読むものにも、どこにも書かれていなかった。
  これが `doc` を必須にした理由である

- 名前は小文字とアンダースコア（`snake_case`）。**アダプタは設計の名前をそのまま使う**
  （Python・TypeScript とも）。正規形に戻すときに訳し戻しが要らないからである。その言語の
  予約語に当たる名前にだけ `_` を付ける（Python の `class` → `class_`、TypeScript の `delete` → `delete_`）。
  record のフィールドは、Python では元の名前をメタデータに持ち、正規形では元の名前に戻す
- **関数名はモジュールの中でだけ一意。** 例の中で依存先の関数を呼ぶときは `rules.buy` のように
  モジュール名を付ける（§8-2）

## 4. 例

例は**データ**であり、コードではない。

```json
{
  "id": "M4.E5",
  "from": "D3",
  "steps": [
    {"let": "s", "value": {"resource": 15.0, "owned": {}, "last_update": 0.0}, "type": "GameState"},
    {"let": "b", "call": "buy", "args": {"state": {"$": "s"}, "catalog": {"$": "CATALOG"}, "name": "cursor"}}
  ],
  "then": {"observe": ["s"], "equals": [{"resource": 15.0, "owned": {}, "last_update": 0.0}]}
}
```

| 項目 | 意味 |
|---|---|
| `id` | `<定義項目またはモジュール>.E<番号>`。記録・トレース・帰責はこの ID で行う |
| `steps` | 順に実行する。`call` は関数を呼んで結果を `let` の名前で持つ。`value` は型つきの値をそのまま持つ |
| `args` | **引数名で**渡す。値は直書きか、`{"$": "名前"}` で前の段の結果や共有の値を指す |
| `then.observe` / `equals` | 最後に、名前の付いた値を期待値と比べる。**比べるのは1回**（複数の値をまとめて比べてよい） |
| `then.observe` / `matches` | **一部だけ**を比べる。レコードは書いた欄だけを比べ、書かない欄は見ない（リストは長さも比べる）。項目が画面の一部について言うなら、画面をまるごと書かずにその部分だけを書く |
| `then.observe` / `holds` | **条件**。観測した値を順に受け取って `true` を返す JavaScript の関数を、ソースの文字列で書く（`"(s, a) => a.player.x === s.player.x"`）。正解がいくつもあるもの（生成したもの、2つの結果の関係、「道がある」）や、正確な値を出すのに手計算が要るものに使う。対象が TypeScript のときだけ |
| `then.raises` | **最後の段が**そのエラーを投げること。それより前の段は成功しなければならない |
| `tol` | 浮動小数の許容誤差。省略時は相対 1e-9・絶対 1e-12 |
| `from` | どの定義項目から起こしたか（任意。トレース用） |

- **入力を変えないこと**は、呼んだあとで入力の名前を観測すれば書ける（`D2.E2`、`M4.E5`）
- 例の中で呼べるのは、そのモジュールの関数と、`depends_on` に書いたモジュールの関数だけ
- **条件（`holds`）の決まり**（DECISIONS 44）: 使えるのは計算のための言語の道具（Math・JSON・Number・String・Array・
  Object・Map・Set など）だけで、Date・Math.random・入出力は使えない（モジュールの参照の検査と同じ一覧）。
  `true` 以外（真に見えるだけの値、例外）は不成立。関門は条件を**実行せずに**読む（箱の中で、構文・関数1つか・
  引数の数・使ってよいものだけか）。**条件が十分に強いかは関門では決めない。** 甘い条件が通したものは、
  ループの評価ができたものを見て見つけ、次の周で直す
- **赤の関門と条件**: 値（`equals`・`matches`）はスタブに対して落ちなければならない（DESIGN §5）。条件は問わない。
  2つの結果の関係を言う条件（壁へ進んでも位置が変わらない）は、同じ番兵ばかり返すスタブでも成り立つ。それで正しい

### 共有の値（fixtures）

```json
"fixtures": {"CATALOG": {"type": "list<GeneratorSpec>", "value": [ ... ]}}
```

`design.json` に置き、例から `{"$": "CATALOG"}` で指す。名前は大文字。例の `let` で同じ名前を使ってはならない。

## 5. モジュール

```json
{
  "id": "M4", "name": "rules", "kind": "pure",
  "depends_on": ["M1", "M2"],
  "functions": { ... },
  "examples": [ ... ]
}
```

| `kind` | 意味 |
|---|---|
| `pure` | 値を受け取り、値を返す。I/O も時計も持たない |
| `assembly` | 組み立て。**ちょうど1つ。** 契約は定義の外部インターフェースと**完全に同じ**。例は定義の例そのもの（機械が写す。`examples` には足したいものだけを書く） |
| `support` | テスト側の道具（偽物など）。例を持ち、使われる前に自分の赤→緑を通す（DESIGN §5）。放置ゲームでは要らなかった |

作る順序は `depends_on` から機械が求める（トポロジカル順）。`design.json` には書かない。

## 6. シェル

**I/O・時計・画面は、シェルにしか無い。** シェルは外部インターフェースの関数を呼び、結果を
プラットフォームとやり取りするだけの薄い層で、例では確かめられない。

| | 持つもの |
|---|---|
| `definition.json` の `shell` | `platform`（`browser-dom` か `browser-3d`。DESIGN §1）と、務めの箇条書き（散文） |
| `design.json` の `shell` | `calls`: 組み立てモジュールの ID |

シェルの中身は例では確かめられない。プラットフォームの起動確認（下）と、できたものの評価（DESIGN §6）が見る。

**出力は1つの HTML ファイル**（DESIGN §1 の目的）。作業場のモジュールとシェルを1つにまとめ、
開けば画面が出る形にする。シェルはアプリごとに書かず、**プラットフォームごとに機械側が用意する汎用の
シェル**が描く。アプリは画面の記述（データ）を返す。

### browser-dom（固定、2026-10-10）

正本は `adapters/platforms/browser-dom/platform.json`。定義がこのプラットフォームを宣言したら、関門が次を確かめる:

- 型 `NodeKind`（enum: `heading`・`text`・`button`）、`Node`、`Screen` を**プラットフォームの宣言と同じ形で**持つ
- 外部インターフェースに次の5つを持つ。`$State` は `start` が返す record 型で、5つを通して同じ型
- 設計の対象言語は TypeScript

| 関数 | シェルがいつ呼ぶか |
|---|---|
| `start(now: float, saved: optional<string>) -> $State` | 開いたとき。localStorage の保存を渡す。保存が読めずに投げたら、`saved` 無しでやり直す |
| `step(state: $State, now: float) -> $State` | 1秒ごと |
| `act(state: $State, action: string, now: float) -> $State` | ボタンが押されたとき。**投げたら状態はそのまま**（買えない、など） |
| `screen(state: $State) -> Screen` | 状態が変わるたび。`Screen {title, nodes: list<Node>}`、`Node {kind, text, action, enabled}` |
| `save(state: $State) -> string` | 状態が変わるたび。localStorage に書く |

シェルは `nodes` を縦に並べる（見出しは `h1`、文は `p`、ボタンは `button`。`enabled` が false なら押せない。
押すと `act(state, action, now)`）。`now` は秒（`Date.now() / 1000`）。保存の鍵は `loop:<定義の title>`。

出力は窓口の `build-app` が作る: 組み立てとシェルを rolldown で1つのスクリプトにまとめて `page.html` に埋め込み、
happy-dom で一度開いて、何かが描かれること・押せるボタンを全部押しても壊れないことを確かめる（`boot.mjs`）。
どちらも exec として走る。見た目と操作感は人間が開いて確かめる。

### browser-3d（固定、2026-10-10）

正本は `adapters/platforms/browser-3d/platform.json`。three.js 0.170.0（`provision/35-node.sh` で固定）の
シーンを汎用シェルが描く。アプリは毎フレーム**シーンの記述（データ）**を返し、three.js には触れない。
関門が確かめることは browser-dom と同じ形で、型と関数が違う:

- 型 `Vec3 {x, y, z}`、`Camera {position, yaw, pitch, fov}`、`Shape`（enum: `box`・`sphere`・`plane`・`cylinder`）、
  `Object3D {id, shape, position, size, rotation_y, color}`、`NodeKind`・`Node`（browser-dom と同じ）、
  `Scene {title, camera, objects: list<Object3D>, hud: list<Node>}`、`Input {keys: list<string>, mouse_dx, mouse_dy, locked}`

| 関数 | シェルがいつ呼ぶか |
|---|---|
| `start(now, saved) -> $State` | browser-dom と同じ |
| `step(state, now, input: Input) -> $State` | **毎フレーム**（約60回/秒）。押されているキーと、前のフレームからのマウスの移動量。投げたら状態はそのままで、そのメッセージを一度だけ console に出す（起動確認はそれで落ちる） |
| `act(state, action, now) -> $State` | シーンのクリック（`"click"`。同時にポインタをロックする）と HUD のボタン。投げたら状態はそのまま |
| `screen(state) -> Scene` | 毎フレーム |
| `save(state) -> string` | 1秒ごとと、act のたび |

約束（`platform.json` の `conventions`。definer のブリーフにもそのまま載る）: 長さはメートル、角度はラジアン、
ただし `fov` は**縦の視野角を度で**。y が上。yaw 0 で -z を向き、yaw が増えると左（上から見て反時計回り）を向く。
pitch が増えると上を向く。向いている方向は (-sin yaw, 0, -cos yaw)、右は (cos yaw, 0, -sin yaw)。
`size` は箱・板・円柱では幅・高さ・奥行き、球では `size.x` が直径。`plane` は x-z に水平に置く。色は `"#rrggbb"`。
キーは `KeyboardEvent.key` の小文字。マウスの移動量はロック中だけ 0 以外。光・影・空はシェルが持つ。
シェルは描く前にシーンを確かめる（id の重複、有限でない数、範囲外の fov、色の形）。

**フレームの速さに依存させない**のはアプリの側: 状態に前回の `now` を持ち、`速さ × (now - 前回)` だけ動かす。
例で確かめられるのはこの形にしたからで、`step` を入力つきで呼ぶ例を定義に書ける。

起動確認（`boot.mjs`）: happy-dom には WebGL が無いので描画はしない。そのかわりシェルの取っ手
（`window.__loop`）から300フレームを決まった入力（前進のあと右へ、マウスを動かし、時々クリック）で回し、
例外が無いこと・シーンが毎回確かめを通ること・カメラが動いたことを見る。本物の描画は人間が開いて確かめる
（見本 `coinroom` は headless Edge でも描けることを確かめた）。

見本: `docs/formats/examples/coinroom.{definition,design}.json`（部屋を歩いてコインを集める。6モジュール）と
その正しい実装 `adapters/typescript/tests/coinroom/`。

## 7. 出口の関門

`engine/artifacts.py`（`check_definition` / `check_design`）。どの指摘も、悪い段（要件定義かモジュール設計か）と
場所を持ち、そのまま帰責（DESIGN §5）に使える。設計の関門は、関門を通らなかった定義に対しては判定しない。
両方向のテスト 26 件（放置ゲームは通り、壊した 24 通りはどれも正しい段・正しい場所で拒まれる）。

### 定義の関門

| 検査 | 落ちたら |
|---|---|
| ID が一意。例の ID が自分の項目の下にある | 要件定義 |
| 例の無いインターフェース関数が無い。どの項目に例が要るかは覆いの関門が決める（§11、§12） | 要件定義 |
| `matches` の値は型の一部（レコードは欄を省ける）。`holds` は文字列で、対象が TypeScript のときだけ | 要件定義 |
| 例の引数名が契約と過不足なく一致し、値が型に合う | 要件定義 |
| 参照（`$`）が前の段か共有の値を指す | 要件定義 |
| `raises` が、最後の段の関数が宣言したエラー | 要件定義 |

### 設計の関門

| 検査 | 落ちたら |
|---|---|
| 定義の型を**同じ形で**持ち、定義のエラーを全部持つ | モジュール設計 |
| 依存先が存在し、循環しない | モジュール設計 |
| 組み立てがちょうど1つで、契約が外部インターフェースと完全に同じ | モジュール設計 |
| シェルの呼び先が組み立て。全モジュールが組み立てから依存をたどって届く | モジュール設計 |
| 全関数に例がある（組み立ては定義の例で満たす） | モジュール設計 |
| 全関数に `doc` がある。契約に知らない欄が無い | モジュール設計 |
| 例が呼ぶのは、自分か依存先の関数だけ | モジュール設計 |
| 定義の例が、組み立ての契約の上でそのまま成り立つ形をしている | モジュール設計 |
| 共有の値が型に合う | モジュール設計 |

試作のあとで足した検査:

| 検査 | 落ちたら |
|---|---|
| 同じ関数・同じ入力（1段の例）に違う期待値（矛盾） | その段 |
| 参照（`$`）の型が引数の型に合う。T は optional<T> に渡してよい | その段 |
| 定義のプラットフォームが `browser-dom` か `browser-3d`（DESIGN §1） | 要件定義 |
| 設計の対象言語にアダプタがあり、プラットフォームが定義と同じ | モジュール設計 |
| 名前の形（関数・フィールド・モジュールは snake_case、型・エラーは CapWords、共有の値は UPPER_CASE） | その段 |
| map のキーに `$` だけを使わない（参照と区別できない） | その段 |

## 8. 試して分かったこと

### 8-1. テストは機械が生成できる

試作は、手で書いたテストを1本も使わずに、**例 46 件を汎用の実行器で参考実装に当てた。**
例は全部データ（呼ぶ関数・引数名つきの値・観測する名前・期待値）なので、テストのコードは
「型に合わせて値を作り、関数を呼び、比べる」の書き写しにしかならない。
アダプタが言語ごとにこの書き写しを生成できる。

**だからテストは機械が生成する**（DECISIONS 決定 2）。v1 の形（関数と値だけ）の範囲では、
テストを書くことに判断の余地が残らない。tester（Claude）は支援モジュールの中身だけを書く。

### 8-2. 関数名はモジュールの中でだけ一意にする

組み立ての `buy(state, name)` と、依存先の `buy(state, catalog, name)` が衝突した。
試作の関門が最初の実行で見つけた。モジュール名で修飾して呼ぶ形にした。
**C には名前空間が無い**ので、C のアダプタは記号にモジュール名を前置する。

### 8-3. 丸めは言語ごとに違う

`50.625` を小数2桁にすると、**Python は `"50.62"`、Node は `"50.63"`**（実測）。
Python は最近接偶数に、JavaScript の `toFixed` は切り上げ側に丸める。

- 数を文字列にする関数は、**丸め方を設計の文で宣言する**
- 期待値は宣言した丸め方で計算する。設計者が自分の言語の既定で計算すると、別の言語で書いたときに落ちる
- 境目（`.xx5`）の例は、その丸め方を固定するために**わざと置く**価値がある

放置ゲームの例は境目を避けている（`33.75`、`100.00`）。避けるか固定するかは設計が選ぶ。

### 8-4. 順序が要るものは list

画面の行は cursor、grandma の順に出したい。カタログを `map` にすると並びが言語ごとに変わるので、
`list<GeneratorSpec>` にした。

### 8-5. 文字列の正確な形は、往復と読み込みで固定する

保存の `encode` の出力は例で固定していない。`15.0` を `15` と書くか `15.0` と書くかが言語で違うからである。
代わりに、**往復（`decode(encode(s)) == s`）と、決まった文字列の `decode`** で、意味のある部分だけを固定した。

### 8-6. run 7・run 8 の組み立ての穴は、関門で止まる

| | 何が欠けていたか | この形では |
|---|---|---|
| run 7 | 最初の資源を得る経路が、どのモジュールにも属していなかった | 定義の項目（`D2` クリック）になり、組み立ての契約に入る。例の無い関数は関門で落ちる |
| run 8 S1 | `app.ts` が作られ、テストされ、出荷物から呼ばれなかった | シェルの呼び先は組み立て。組み立てから届かないモジュールは関門で落ちる |

## 10. 記録

比較関数が書き出す、判定の元になるもの（DESIGN §5）。**どの言語でも同じ形**で、
`$LOOP_RECORD_DIR/records.jsonl` に1行1件、書くたびに flush する。

```json
{"t": "start", "id": "M2.E1"}
{"t": "check", "id": "M2.E1", "ok": true,  "expected": [33.75], "actual": [33.75]}
{"t": "check", "id": "M1.E3", "ok": false, "expected": {"raises": "UnknownGenerator"}, "actual": {"returned": {"name": "x"}}}
```

| 形 | 意味 |
|---|---|
| `start` のあと同じ ID の `check` | 比べた。`ok` が結果 |
| `start` だけ | 比べる前に落ちた（例外・クラッシュ）。理由はテストフレームワークの出力から読む |
| どちらも無い | そのテストは走らなかった（ビルドできない、など） |

- `expected` / `actual` は §2 の正規形。値の例は `then.equals` と同じく**観測する値の並び**、
  エラーの例は `{"raises": 名前}` と、実際に起きたこと（`{"raises": 名前}` か `{"returned": 値}`）
- 期待値はテストに書かない。比較関数が `LOOP_EXAMPLES`（窓口が用意する例のファイル）から読む
- Python の実装: `adapters/python/loopcheck.py`

### 例のファイル

アダプタは作業場の直下に `examples.json` を置き、`exec-run` がそれを `LOOP_EXAMPLES` として渡す
（全言語共通の決まり）。中身は設計の全部の例で、組み立てモジュールには定義の例が入る。
各段には、言語に依らない中核（`adapters/design.py` の `examples_file()`）が次を書き足す:

| 書き足すもの | 用途 |
|---|---|
| `module` / `function` | `rules.buy` のような修飾を解いた、呼ぶ先 |
| `arg_types` | 各引数を、どの型として組み立てるか |
| `returns` | 戻り値の型 |

生成されたテストは、入力も期待値も直書きしない。入力は段と引数名で比較関数に頼み
（Python では `loopcheck.arg(ex, 段, 名前)`）、型どおりに組み立てられた値を受け取る。
前の段の結果を指す参照（`$`）だけは、テストの中の変数になる。

## 11. 概念ファイル（`concepts.json`）（2026-10-13 実装。関門は `engine/artifacts.py` の `check_concepts`・`check_coverage`）

要求分析の出力（DESIGN §4）。**全員が参照する原本は、このファイル1つ**にする。概念の意味も、満たすべき
要件も、範囲外もここに持つ。原本が2つあると、どちらが正しいかを読み手が決めることになり、意味がまた揺れる。

- 書くのは要求分析の段（`analyst`）だけ。ほかの段は読むだけ
- **何を作るかは書かない。** 書くのは、要求の言葉の意味と、要求者の目的に届くために必要なこと。何を作るかを
  決めるのは定義（definer）で、定義はこのファイルに照らして関門にかけられる
- `request` は機械が要求の原文をそのまま入れる（分析役には写させない）
- `background` は任意の自由な文脈。必須でも関門の対象でもない
- `requirements`（必要なこと）は、要求者が**達成したい状態**で書く（「月ごとにいくら使ったかが分かる」）。
  機能・画面・ボタンの形で書かない ── それを選ぶのは definer
- 正本はホストの `apps/<名前>/concepts.json`。通しごとに `runs/<run>/` へ写しを残す
- 賢い役（definer・designer・評価役）には丸ごと渡す。弱い役（9B）には、参照する項目だけをエンジンが
  ブリーフの本文に展開する

```json
{"format": "loop/concepts@1",
 "request": "<人が書いた要求の原文、全文>",
 "concepts": [
  {"id": "C1", "name": "迷路", "kind": "thing", "status": "active",
   "source": "小さな迷路を歩いて、出口を目指す",
   "meaning": "マスが格子に並び、隣り合うマスの間に壁があるかないかが決まっている。スタートとゴールのマスがある",
   "properties": [
    {"id": "C1.P1", "text": "スタートからゴールへ、壁を通らずに行ける道がある", "check": "example"},
    {"id": "C1.P2", "text": "道が分かれるマスが少なくとも1つある", "check": "example"},
    {"id": "C1.P3", "text": "行き止まりが少なくとも1つある", "check": "example"},
    {"id": "C1.P4", "text": "歩いていると、どちらへ行けばよいか迷う", "check": "evaluation"}],
   "not": ["1本道は迷路ではない", "壁の無い部屋は迷路ではない"]},
  {"id": "C5", "name": "何をすればよいか分かる", "kind": "quality", "status": "active",
   "source": "（共通の質の概念: アプリは説明なしで開かれる）",
   "meaning": "開いた人が、説明を読まずに、何のアプリで、どう操作し、何を目指すのかが分かる",
   "properties": [
    {"id": "C5.P1", "text": "最初の画面に、題名・操作・目的が文字で出ている", "check": "evaluation"}],
   "not": ["最初の画面が単色の面だけ", "経過時間しか出ていない"]}],
 "requirements": [
  {"id": "R1", "text": "最初の画面に題名と操作方法とゴールの見つけ方を出す", "status": "active",
   "source": "implied", "reason": "要求には無いが、アプリは説明なしで開かれるため",
   "check": "evaluation", "concepts": ["C5.P1"]},
  {"id": "R2", "text": "クリアしたら、かかった秒数を出す", "status": "active",
   "source": "ゴールのマスに入るとクリア。画面の左上に「クリア！」とかかった時間（秒）を出す",
   "reason": "要求にある", "check": "example", "concepts": []}],
 "out_of_scope": ["敵や罠", "迷路の自動生成", "音"]}
```

| 欄 | 中身 |
|---|---|
| `request` | 人が書いた要求の原文、全文。言い換えない |
| `concepts[].kind` | `thing`（物事の概念）か `quality`（質の概念）。質の概念は評価の基準になる |
| `concepts[].source` | 要求の該当部分を**そのまま**引く。共通の質の概念は、どこから来たかを書く |
| `concepts[].meaning` | 何でできているか。**それだけで読める文**にする |
| `concepts[].properties` | 必ず成り立つこと。性質ごとに番号と確かめ方を持つ |
| `properties[].check` | `example`（定義の例で確かめる）か `evaluation`（できたものを見て確かめる） |
| `concepts[].not` | 反例。「これは違う」。弱いモデルには特に効く |
| `requirements[]` | 満たすべきこと。`source` は要求の該当部分か `implied`、`implied` なら `reason` が必須 |
| `out_of_scope` | 作らないもの。改良が際限なく広がるのを止める |
| `status` | `active` か `retired`。消すときは `retired` にして残す |

**決まり:**

- **番号は振り直さず、使い回さない。** 概念は `C<n>`、性質は `C<n>.P<m>`、要件は `R<n>`。参照と指紋が壊れないように
- **各文はそれだけで読める。** `meaning`・`text`・`not` は、ほかの項目や番号を参照しない（DESIGN §4 の自己完結）。
  番号で結ぶのは構造化された欄（`requirements[].concepts`）だけ
- **参照は欄で書く。** `definition.json` の各項目と `design.json` の各モジュールに `"concepts": ["C1.P2", "R1", …]` の
  欄を加える。散文の中には番号を書かない

**関門:**

| 関門 | 見ること |
|---|---|
| 概念ファイルの関門 | 形式、番号の形と重複、`check` の値、`implied` の要件に `reason` がある、散文が他の項目を参照していない |
| 覆いの関門（定義の出口） | 2段に分かれる（§12）。definer の出口: `check: "example"` の性質と要件が、どれかの定義項目の `concepts` 欄から参照されている。定義に `summary`（何を作るか）がある。存在しない・廃止された番号を参照していない。足りなければ definer に戻す。tester の出口: `check: "example"` のものを参照する項目は、例を持つ。足りなければ tester に戻す。`check: "evaluation"` だけを参照する項目は例が要らない（評価の段で見る） |
| 改良のとき | 前の定義の例が残っている。`retired` でない性質と要件の覆いが減っていない |

## 12. 定義の書き分け（2026-10-15 実装、DECISIONS 44。関門は `engine/artifacts.py` の `check_draft`・`check_examples`）

要求から作るとき、`definition.json` は3者で書く。definer は**何を作るか**だけを書き、判断の要らない部分は機械が、
例は tester が書く。最後に機械が1つの `definition.json` にまとめ、設計から先はこれまでと同じものを読む。

| 部分 | 書くもの | 書き手 |
|---|---|---|
| 何を作るか | `title`・`summary`・アプリの状態（`state` とその型）・エラーとどの関数が投げるか（`raises`）・項目（`id`・`title`・`statement`・`concepts`） | definer |
| プラットフォームの部分 | プラットフォームの型、5つの関数（`$State` をアプリの状態に置き換え、`raises` を付ける）、`shell.platform` | 機械（`complete`） |
| 例 | 項目ごとの例。合否の基準は値・一部の値・条件（§4） | tester |

**definer が書くもの**（`definition.json`。例と関数とシェルの務めは書かない。書けば関門が戻す）:

```json
{"format": "loop/definition@1",
 "title": "迷路",
 "summary": "格子の迷路を歩いてゴールを目指すアプリ",
 "state": "MazeState",
 "types": {"MazeState": {"record": [{"name": "x", "type": "int"}, {"name": "y", "type": "int"}]}},
 "errors": {"NotAllowed": "その操作は今はできない"},
 "raises": {"act": ["NotAllowed"]},
 "items": [{"id": "D1", "title": "壁は通れない", "statement": "壁のある方向へ進む操作をしても、位置は変わらない",
            "concepts": ["C1.P1"]}]}
```

- 項目の文は、概念ファイルを読んでいない人でも確かめ方を書けるほど具体的に書く（どの状態で、どの操作をすると、
  何が成り立つか）。正解がいくつもあるもの（生成した配置など）は、どの正解にも共通することを書く
- 項目は必ず、応えている性質か要件を1つ以上 `concepts` に持つ
- プラットフォームの型をアプリの型として書かない（機械が入れる）

**tester が書くもの**（`examples.json`）:

```json
{"format": "loop/examples@1",
 "items": {"D1": [{"id": "D1.E1", "steps": [...], "then": {"observe": ["s", "a"], "holds": "(s, a) => a.x === s.x && a.y === s.y"}}]}}
```

- tester が読むのは、定義の型・エラー・関数と、項目の文と、項目が応えている性質・要件の文と反例だけ。
  概念ファイル全体は読まない。項目の文の言い足りなさは、definer の意図と違う例として表に出る
- 例の書き方は §4 と同じ。プラットフォームの `platform.json` の `examples` が、そのプラットフォームでの固め方を言う
  （画面は項目が言う部分だけを `matches` で、など）

**関門:**

| 関門 | 見ること | 戻す先 |
|---|---|---|
| 下書きの関門（`check_draft`） | 書いてよい欄だけ、状態がレコード型、`raises` がプラットフォームの関数と宣言したエラー、項目の形、散文に番号が無い、覆い（§11）、機械がまとめた定義が定義の関門を通る（関数の例は除く） | definer（要件定義） |
| 例の関門（`check_examples`） | 形式、知らない項目が無い、まとめた定義が定義の関門を通る、`check: "example"` を参照する項目が例を持つ | tester（定義の例） |
| 条件の読み取り（窓口 `check-conditions`） | 条件ごとに、構文、関数1つだけか、引数の数が観測する値の数と同じか、使ってよいものだけか。箱の中で、実行せずに読む | tester（定義の例） |

手で書いた定義（`formats/examples/` の放置ゲームなど）は、これまでどおり1つのファイルで、プラットフォームの
5つより多くの関数を持ってよい。要求から作る定義の関数は、プラットフォームの5つだけになる。
