# DESIGN.md — 何を、どういう考えで作るか

この文書が設計の本体である。ほかの文書は、それぞれそれだけで読めるように分けてある:

| 文書 | 中身 |
|---|---|
| **DESIGN.md**（これ） | 目的、流れ、各段、デバッグ（関門と帰責）、外側の輪、言語とプラットフォーム |
| [SYSTEM.md](SYSTEM.md) | どこに置き、どう守るか。ホストと箱、役と uid、窓口、正本、台帳、箱の作り方の考え方 |
| [FORMATS.md](FORMATS.md) | 定義・設計・概念ファイル・記録の形 |
| [DECISIONS.md](DECISIONS.md) | 決まったこと（いつ・何を・なぜ）と、決まっていないこと |
| [PROGRESS.md](PROGRESS.md) | 進み具合。済んだこと、通しの結果、次にやること |

**未実装**と書いた箇所は、設計として決めたがまだ作っていないもの。何が動いているかは PROGRESS.md にある。

## 1. 目的と考え方

### 目的

**要求を入れると、開けばそのまま動くアプリを出力する。**

- 人が書くのは**要求**（欲しいものの言葉）。何を満たせばよいか（**要件**）は機械が分析して書く（§4）
- 出力は**1つの HTML ファイル**。必要なものを全部埋め込み、ダブルクリックするとブラウザで開いて
  アプリの画面が出る。インストールは要らない
- **1周目は MVP。そこから機械が観点ごとに改良を重ね、一通り完成させる**（§6、未実装）。
  例で書ける約束は機械がテストで確かめ、できたものは機械が動かして次の改良を考える。
  人が入るのは、一通り完成したときと、必要なリソースが無いとき
- アプリは**ブラウザのサンドボックスの中で動く**。生成されたコードがホストを直接触ることはない
  （箱の外で動く唯一の生成物なので、ここは譲らない）。出力には CSP を付けて外へ通信させず、生成コードが
  許可していないもの（`fetch`・`document`・`eval` など）を使っていないかを試行ごとに確かめる（§5・§7）。
  時刻も乱数も、モジュールが自分で取りに行かず、呼び出す側（シェル）から引数で受け取る
- **機構は汎用である。** いまの題材がゲームなのは、できたものを確かめやすいからで、ゲームを作ることは目的ではない

### プラットフォーム

アプリをどう届けるかは、要求からアプリを作るときに人が選ぶ（アプリの `platform`）。

| | プラットフォーム | 画面 | 作れるもの |
|---|---|---|---|
| ① | `browser-dom` | DOM | 表示とボタンで遊ぶもの（放置ゲームなど） |
| ② | `browser-3d` | three.js（WebGL） | 3D で歩いて見回すもの |
| ③ | 静的サイト・Next.js ＋ デプロイ | ── | **後で**。デプロイはホストから、人の確認のあとで、ホストの鍵で行う |

表現の幅はライブラリで決まる。solver も exec も外へ通信できないので、**ライブラリはプラットフォームごとに
箱を作るときに版を固定して入れる**（three.js 0.170.0 など）。誰が何を持ち込んだかが常に分かる。

**アプリごとに書かれる、確かめられないコードを無くす。** アプリのロジック（移動・当たり判定・得点・
カメラの計算）は純粋なモジュールにして例で確かめ、画面には「何をどこに描くか」という**画面の記述**
（データ）だけを返させる。記述を DOM や three.js に描く部分は、**プラットフォームごとに機械側が用意する
汎用のシェル**が担う（§7）。

### 考え方

**定義と設計を部分的に、深く書く。そうすれば実装は狭い仕事になり、弱いモデルでも担える。**

- 要求を分析し（概念ファイルと要件、§4）、定義し、**モジュール単位まで**設計する
- **各層の文書は、それだけで完結する**（§4）。上の層の文章を参照して意味を省かない
- 設計からテストを機械が起こし、テストに合わせて弱いモデルが実装する
- テストが落ちたら、**落ちた場所でどの段が悪いかが決まる**ように流れを組む（§5）
- できたものは機械が動かして観点ごとに改良案を出し、改良ファイルとして積んで作り直す（§6）
- 段から段への進行と戻りを、**人ではなく機械がループとして回す**
- その機構は**サンドボックスの外**（ホスト）に置き、1つの流れとしてプログラムに書く。
  LLM と、生成されたコードの実行はサンドボックスの中に置く（SYSTEM.md）
- **言語を選ばない。** 言語ごとの差はアダプタに閉じ込める（§7）

## 2. 流れ

```
要求（人）
  → 要求分析 → 要件定義 → モジュール設計 → テスト作成 → 実装 → 出力 ─┐
                  ▲            ▲              ▲          ▲              │
                  └────────────┴──────────────┴──────────┘              │
                       落ちた場所が、悪い段を指す（§5）                    │
                                                                        ▼
                  ┌──── 改良ファイル（定義の周）◀── 評価（観点ごとの改良案）
                  │     設計のやり直し（設計の周）◀── レビュアー（保守性）
                  ▼
           観点を固定の順に1回ずつ通す（§6）→ 一通り完成 → 人
```

| 段 | 受け取る | 出す | 担い手 | 出口で確かめること |
|---|---|---|---|---|
| 要求分析 | 要求 | 概念ファイル `concepts.json`（概念・性質・要件・範囲外） | 分析役（Claude、新しい uid。**未作成**） | 概念ファイルの関門。人の確認（**未実装**、要否は DECISIONS 未決 1） |
| 要件定義 | 概念ファイル | 最初の定義 `definition.json`（外部インターフェースと、項目ごとの例）。1周目の MVP | definer（Claude） | 定義の関門、覆いの関門（覆いは**未実装**） |
| モジュール設計 | 定義（2周目からは機械が作った「今の定義」） | `design.json`（モジュール・契約・doc・依存・例・組み立て） | designer（Claude） | 設計の関門 |
| テスト作成 | 設計の1モジュール分 | 型・スタブ・テスト | **機械**（アダプタが例から生成）。支援モジュールだけ tester（Claude） | 赤の関門（スタブに対して落ちること） |
| 実装 | そのモジュールのブリーフ | そのモジュールのファイル1つ | **solver**（ローカルの 9B） | 検証（自分の例と、前に緑だった例、参照の検査） |
| 出力 | 緑の組み立てと汎用シェル | `app.html` | **機械**（窓口の `build-app`） | 起動確認 |
| 評価 | 動かした証拠と概念ファイル | 観点ごとの改良案 | 評価役（critic の uid。コードも定義も読まない） | ──（**未実装**） |
| 改良 | 改良案、コード | 改良ファイル（定義への追記）。保守性では設計への指摘 | レビュアー（definer の 2周目からの呼び名） | 改良ファイルの関門（**未実装**） |

**各段の出力は機械が読める形にする。** 関門は「定義が概念ファイルを覆っているか」「設計が定義の例を
含んでいるか」を突き合わせるので、突き合わせる相手が散文だと検査できない。形は FORMATS.md。

実装されている流れ（2026-10-10）は、要求から definer が直接定義を書くところから、出力の起動確認まで。
要求分析・評価・改良は未実装で、いまは人がその役をしている。

## 3. なぜ深く設計するのか

### 弱いモデルは、狭い範囲なら実装できる

| いつ | 何をしたか | 結果 |
|---|---|---|
| run 6（旧い形） | 旧い計画のまま、ソルバーをローカルの 9B に替えた | 11/11 を全ステップ1回で緑 |
| run 8（旧い形） | 9B が S1・S2・S4 を実装 | 実装は1回目で緑。ただし S1 は**文脈長で落ちた** ── 範囲が広すぎた |
| 2026-10-10 | 放置ゲームを今の形で（設計が `doc` を持ち、`format` を分けたあと） | **8 モジュールすべて1回目で緑**（89 秒） |
| 2026-10-10 | 3D 迷路を要求から | **6 モジュールすべて1回目で緑** |

範囲が広すぎれば弱いモデルは落ちる。範囲を狭めることはこれに直接効く。

### 「深い」とは、判断を上流に寄せること

設計がシグネチャ、依存先、どう計算するか（`doc`）、具体的な入出力の値まで決めていれば、実装は
**判断ではなく書き写し**になる。弱いモデルに残すのは書き写しだけにする。

### 組み立ても設計の一部にする

分割を細かくするほど、**モジュールの「間」にあるもの**が増える ── どれがどれを呼ぶか、
初期状態、起動経路。ここが誰の担当でもないと、部分は全部正しいのに全体が動かない。
旧い形では実際にそうなった:

- run 7: `production_rate` も `buy_generator` も `view` も正しかった。欠けていたのは
  「最初の資源を得る経路」で、**どのモジュールにも属していなかった**
- run 8 S1: `app.ts` は**作られ、テストされ、出荷物から呼ばれなかった**

だからモジュール設計は、モジュールの一覧だけでなく**組み立て**も1つの設計物として持つ。
組み立ては小さな実装単位（組み立てモジュール）として切り出し、弱いモデルの範囲に収める。
**組み立てモジュールのテストは、定義の例そのもの**である（§5）。

## 4. 要求分析と概念ファイル

### 要求と要件

| 言葉 | 何か | 誰が書くか |
|---|---|---|
| **要求** | 欲しいものの言葉（「3D の迷路を歩いて出口を目指したい」） | 人 |
| **要件** | 何を満たせばよいか。書かれていないが当然要るものを含む | 要求分析 |
| **概念ファイル**（`concepts.json`） | 要求の言葉の意味（迷路とは何か、何でないか、どう確かめるか）。**要件もここに持つ** | 要求分析 |
| **要件定義**（`definition.json`） | 機械が確かめられる約束（型・関数・項目と例） | definer |

### なぜ要るのか ── 意味は段を渡るたびに縮む

2026-10-10、要求から 3D の迷路を作った。テストは全部緑、起動確認も通ったのに、開くと**何か分からない**
ものができていた。迷路は分かれ道の無い1本道だった。

「迷路」の意味は、definer の時点で落ちていた。definer（Claude）は迷路が何かを知っているが、定義では
「各行の仕切りに切れ目が1つ」というつづら折りに縮めた ── 要求の「形は固定でよい」を満たす一番簡単な形に。
designer も 9B も定義どおりに正しく作ったので、誰も間違えていないのに「迷路」はどこにも残らなかった。

意味が落ちる理由は2つある:

1. **知能の差。** 上流が当然知っている概念（迷路には分かれ道と行き止まりがある）を、下流は知らない
2. **段を渡るたびに縮む。** 賢い役でも、次の段に渡すときに満たしやすい形に言い換える。元の概念が
   残っていなければ、抜けたことに誰も気づけない

要求分析は、AI が**要求の言葉がどういう概念か**を理解し、それを書き残す層である。流れの最初に置く。

### 概念ファイル

概念の各項目は、確かめられる形で書く。散文の説明だけでは弱いモデルに効かず、評価にも使えない。

| 欄 | 中身 | 迷路の例 |
|---|---|---|
| 出どころ | 要求のどの言葉か（原文をそのまま） | 「小さな迷路を歩いて、出口を目指す」 |
| 意味 | 何でできているか | マス、マスの間の壁、スタート、ゴール |
| 必ず成り立つこと | 確かめられる性質。性質ごとに番号と確かめ方を持つ | スタートからゴールへの道がある（例で）。分かれ道がある（例で）。行き止まりがある（例で）。迷う感じがする（評価で） |
| これは違う | 反例。弱いモデルには「何ではないか」が特に効く | 1本道は迷路ではない。壁の無い部屋は迷路ではない |

概念は2種類ある。**物事の概念**（迷路・壁にぶつかる・クリア）と、**質の概念**（何をするか分かる・
壁と床が見分けられる）。質の概念は評価の基準になる。どのアプリにも共通の質の概念（説明なしで開いた人が
何をすればよいか分かる、など）は、プラットフォームごとに用意して分析に渡す（DECISIONS 未決 10）。

**要件**は満たすべきことの一覧で、要求に書かれていないが当然要るものも**理由をつけて**書く
（「最初の画面で題名と操作と目的が分かる ── 説明なしで開かれるので」）。**範囲外**も書く。
改良が際限なく広がるのを止めるためである。

**全員が参照する原本は、概念ファイル1つに限る。** 要求の原文・概念・要件・範囲外をすべてここに持つ。
原本が2つあると、どちらが正しいかを読み手が決めることになり、意味がまた揺れる。

| 点 | 決めたこと |
|---|---|
| 正本 | ホストの `apps/<名前>/concepts.json`。通しごとに `runs/<run>/` へ写しを残し、その回が何を基準にしたかを後から辿れるようにする |
| 書き換え | **要求分析の段だけ**が書く。ほかの段は読むだけ。**改良では変えない**（改良は改良ファイルに積む、§6）。目的・完成形・MVP の範囲は書かない ── 概念ファイルは要求を分析した概念だけを持つ |
| 届け方（賢い役） | definer（レビュアー）・designer・評価役には、ブリーフと一緒に丸ごと渡す |
| 届け方（弱い役） | 9B にはファイルを渡さない。エンジンがブリーフを作るとき、そのモジュールが参照する項目**だけ**を本文に展開する。9B は全体を読む余裕も、参照をたどって当てはめる力もあまりない |
| 番号 | 概念は `C1`、性質は `C1.P2`、要件は `R1`。**一度振った番号は振り直さず、使い回さない。** 消すときは「廃止」の印をつけて残す。参照と指紋が壊れないように |
| 参照の書き方 | 定義の項目と設計のモジュールに、構造化された欄（`"concepts": ["C1.P2", …]`）を持たせる。散文の中には番号を書かない |
| 変わったとき | 参照している項目の中身を指紋（§5）に含める。項目が変われば、それを参照する定義の項目とモジュールが作り直しの対象になる |

**参照できるだけでは足りない。** 迷路の definer は要求を見られる状態でつづら折りに縮めた。原本が見えていても、
使わなければ同じことが起きる。そこで**覆いの関門**が、概念ファイルの各性質と要件が定義の例で確かめられているか、
評価の基準として残されているかを見て、どちらでもなければ指摘として definer に戻す（§5）。形は FORMATS §11。

### 各層の文書は、それだけで完結する

AI は優秀なので、一度出た言葉を復唱しない。上の層の文章を前提に、その具体案から話し始める。すると
**下の層の文章は、上の層を見ないと意味が分からない形**になり、その下から見ると、元がどういう定義だったかを見失う。
迷路の定義がそうなっていた:

- 「**D1で定めた**壁（wall_s, wall_n, …）」
- 「**D2の** start(now, null) **相当**の初期状態」
- 「迷路は7×7マスの固定レイアウト」── 具体的な配置から始まり、その配置が満たすべき性質（迷えること）が書かれていない

工場で部品を作る作業員は、全体が何になるかを知らない。それでも部品のマニュアルには、その部品を作って合否を
判定するのに必要なことが**全部**書いてある（寸法・公差・材料・検査の仕方）。共通の規格書は参照するが、
上の工程の作業指示書は見に行かない。作業員が自分の作業をこなせば、上の工程が組み合わせて全体ができる。
ここから2つの約束を取る:

1. **各層の文書は、それだけで完結する。** 上の層の文章を参照しない。必要なことは自分の層の言葉で書く。
   参照してよいのは全員共通の原本（概念ファイル）だけで、それも番号で、構造化した欄に書く
2. **全体の意味は、分けた層が持ち続けて確かめる。** 分けた側が、部品の組み合わせが自分の受け取った仕様を
   満たすことに責任を持つ。作業員は全体を知らなくてよい

| 層 | 自分の文書だけで完結させること | 分けたあとに確かめること |
|---|---|---|
| 要求分析 | 要求の言葉の意味を、原文と一緒に書き切る | 要件定義が、概念ファイルの性質を全部覆っているか（覆いの関門） |
| 要件定義 | 各項目が、他の項目を参照せずに読める | 設計の組み立てが、定義の例を全部満たすか |
| モジュール設計 | 各モジュールのブリーフが、それだけで実装できる | 組み立ての例 |

崩れやすいのは上の方の層である。賢い役同士だと「言わなくても分かる」で省略が起き、それが下に落ちる。
一番下の 9B のブリーフは、契約・doc・例を全部入れるので、すでにこの形に近い。

### 人が確かめる場所

人が確かめるのは、要求分析が終わったところが一番安い。「迷路とはこういうもの、と理解した」「作るのはこれ、
合格はこれ」を見て、違えばその場で直せる。何も作る前だからである。確認を必須にするかは DECISIONS 未決 1。

## 5. デバッグ ── 落ちた場所が、悪い段を指す

**テストが落ちた場所だけで、どの段が悪いかが決まるように作る。** 落ちたあとで推理するのではなく、
各段の誤りが**その段に対応する場所でしか表に出ない**ように流れを組む。判定は機械が行い、モデルに判断させない。

### 落ちたあとに推理する表では足りない

旧い形では、検証が落ちると戻り先は常に実装だった。テストのほうが間違っていても止まらない。
run 8 の S5 では、`return storage.getItem(KEY)` という**完全に正しい実装が6回書かれて6回落ちた**。
テストが自前で書いた偽 Storage が `data[key] || null` で、`""` を `null` に潰していたため。
run 8 の未解決の失敗3件（期待値リテラルの `{}` 落ち、存在しないマッチャ `deepEquals`、上記）は
**どれもテスト側の誤り**で、どれも実装に戻され続けた。

「観測 → 判定」の表を作って落ちたあとに推理しても、S5 はどの行にも当たらない。偽 Storage は例外を投げず、
間違った値を返すだけで、テストの期待値 `""` は設計とも一致しているからである。
**テストの中に、検証されていないロジックがある限り、観測で捉えられない誤りが残る。**
だから表を精密にするのではなく、誤りが入り込む余地を潰し、潰しきれないものは**その段の出口で**止める。

### 3つの仕掛け

1. **テストは誰にも書かせない。** 設計の例はデータ（呼ぶ関数・引数名つきの入力・期待値）なので、
   テストは「値を作り、呼び、1回だけ比べる」の書き写しにしかならない。**アダプタが例から生成する**
   （FORMATS §8-1）。期待値のリテラルも、テストフレームワークの API も誰も打たない
2. **テストの中にロジックを置かない。** 偽物・ヘルパなど、判断を含むテスト側のコードは**支援モジュール**として
   設計に載せ、例を持たせ、使われる前にそれ自体の赤 → 緑を通す。中身は tester（Claude）が書く。
   S5 の偽 Storage なら「`setItem(k, "")` のあと `getItem(k)` は `""`」という例で、使われる前に落ちる（**未実装**）
3. **整合は各段の出口で確かめる。** 概念ファイルと定義、定義と設計、設計とテストの突き合わせを、失敗のあとではなく
   次の段へ渡す前に行う。**凍結されてから見つかるテストの誤りを無くす**

### テストの形

アダプタが生成するテストは、どの言語でもこの形になる（擬似コード）。

```
ex = example("M2.E1")                            # 設計の例を読む（入力と期待値）
p  = current_cost(ex.arg(0, "spec"), ex.arg(0, "owned"))   # 段ごとに、引数名で値を作って呼ぶ
check(ex, [p])                                   # 観測する値を1回だけ比べる。期待値は ex が持つ
```

- `example` / `check` / `check_raises` は機械が言語ごとに配る（§7）
- 比較は言語に依らない正規形で行う。浮動小数は 1e-9 まで同じとみなす
- 比較関数は**記録**を残す（`start` と `check`、FORMATS §10）。**判定はテストフレームワークの報告ではなく、
  この記録から読む。** フレームワークは走らせ役にすぎず、言語ごとの報告形式の差はここで消える
- 入力は**引数名で**持ち、生成器が契約の引数の並びに当てはめる。同じ型の引数を取り違える余地も無い

### 関門と帰責

```
要求分析 ── 出口: 概念ファイルの関門・人の確認 ────────────────────────────┐
 要件定義 ── 出口: 定義の関門・覆いの関門                                      │
  モジュール設計 ── 出口: 設計の関門 → スタブ生成 ── 組み立ての検証（定義の例）  │
   テスト生成 ── 出口: 赤の関門（スタブに対して）→ 凍結                         │
    実装 ── 検証（モジュールの例・前の緑）                                       │
     出力 ── 起動確認                                                           │
      評価 ── 指摘が悪い段を指す ◀──────────────────────────────────────────────┘
```

| 落ちた場所 | 何が起きたか | 悪い段 |
|---|---|---|
| **概念ファイルの関門**（未実装） | 形式違反 / 番号の重複 / `implied` の要件に理由が無い / 散文が他の項目を参照している | 要求分析 |
| **定義の関門** | 形式違反 / 例の無い定義項目 / 同じ入力に違う期待値 / プラットフォームの型と関数を持たない / 選ばれたのと別のプラットフォーム | 要件定義 |
| **覆いの関門**（未実装） | 概念ファイルの性質か要件が、定義の例でも評価の基準でも覆われていない | 要件定義 |
| **自己完結の関門**（未実装） | 散文が他の項目・モジュールを参照している（「D1で定めた」「相当」「上記」） | その文書を書いた段 |
| **設計の関門** | 形式違反 / 依存の循環・未解決 / 組み立てから到達できないモジュール / 例の無い関数 / doc の無い関数 / 同じ入力に違う期待値 | モジュール設計 |
| | 定義の例が、組み立てモジュールの例として**そのまま**含まれていない | モジュール設計 |
| **スタブ生成** | 設計の関門を通った契約から、アダプタがビルドできるスタブを作れない | **エンジン**（人へ） |
| **赤の関門** | 生成したテストがビルドできない / `start` が無い / 例が抜けている / `check` が1回でない | **エンジン**（テスト生成器） |
| | `start` のあと `check` が無い（スタブに対して例外で落ちた） | **エンジン** ── テストもスタブも契約から機械が作るので、合わないのは機械の誤り |
| | 関数の結果を観測する例が、スタブに対して通ってしまう | **エンジン** ── 番兵は設計の全期待値と衝突しないよう機械が選ぶ |
| | 支援モジュールの例が、tester の書いた支援モジュールで緑にならない | テスト作成（tester） |
| **検証**（試行ごと） | 自分の例が落ちる / 例外 | 実装（もう一度） |
| | 前に緑だったテストが落ちる | 実装（もう一度） |
| | 設計で宣言していないモジュール、または許可していないグローバル（`fetch`・`document`・`eval` など）を参照している（参照の検査。テストを走らせる前に棄却する） | 実装（その試行は棄却して、もう一度） |
| | solver が動かない（ブリーフが文脈に入らない、推論サーバに届かない） | **エンジン**（人へ） |
| **検証**（試行を使い切った） | 全試行が「宣言外の参照」 | モジュール設計（境界: 依存が足りない） |
| | 全試行が「前の緑を壊す」 | モジュール設計（境界: ぶつかっている） |
| | それ以外 | モジュール設計（粒度: 分割し直す） |
| **組み立ての検証**（使い切った） | 部品は全部緑なのに、定義の例が通らない | モジュール設計（分解・組み立て） |
| **起動確認** | 束ねられない / 開いても描けない / 押せるボタンや決まった入力で壊れる | **エンジン**（シェル・束ね方）── 例は全部緑なので |
| **定義の周**（未実装） | 改良を積んだ定義が、戻りを使い切っても緑にならない | レビュアー（訂正を追記するか取り下げる、§6） |
| **設計の周**（未実装） | 分け直した設計で、前の例が緑にならない（使い切り） | designer。上限に達したら分け直しを見送る（§6） |

**読み方:** 凍結より前で落ちれば、その段が悪い。赤の関門で落ちれば、生成したテストなら機械、支援モジュールなら
tester が悪い。凍結のあとで落ちれば実装が悪く、使い切れば設計が悪い。**テストが凍結のあとで悪者になる経路は、
3つの仕掛けで塞いである。** 例が全部緑でもできたものに足りないところがあれば、それは外側の輪で評価役が見つけ、
改良案にする（§6）。

赤の関門で「スタブに対して落ちる」を求めるのは、**関数の結果を観測する例だけ**である。入力を変えないことを
確かめる例（呼んだあとで入力を観測する、FORMATS §4）は、何もしないスタブに対しても通るのが正しい。

エンジンの誤りは人に上げる。どの段に戻しても直らないからである。アダプタの適合テスト（§7）が、
これを通しの前に潰しておく網になる。

### 使い切ったら、なぜ設計なのか

凍結された時点で、各テストが**設計の例そのものを、契約どおりの呼び方で**比べていることは確かめてある。
それでも通らないなら、残る原因は設計の側にしかない ── 範囲が弱いモデルには広すぎる、依存が足りない、
境界がぶつかる、例どうしが矛盾している。**直すのは実装ではなく、分け方である。**

### 機械が判定できないもの

| | なぜ | 扱い |
|---|---|---|
| 設計の例どうしの一般的な矛盾 | 「同じ入力に違う期待値」以外は機械で見つからない | 使い切り → 設計へ。満たせなかった例の ID を渡す |
| 要求の意図の取り違え | 要求は人の言葉 | 要求分析が概念と要件に書く（人がそこで確かめるかは DECISIONS 未決 1）。定義がそれを覆っているかは覆いの関門が、できたものに足りないところは評価役が動かして見る |
| エンジン（アダプタ・テスト生成器・比較関数・シェル）の誤り | どの段のせいでもない | 適合テスト（§7）で先に潰す。起きたら人へ |
| 記録の偽装 | 比較関数の記録はテスト対象のコードと同じプロセスで書かれる | 実行は専用の uid（exec）。台帳と正本には触れられないが、同じプロセス内の偽装は防げない。弱いモデルが狙って行うことは想定しない |

### 戻すときに渡すもの

| 戻り先 | 渡す | 渡さない |
|---|---|---|
| 実装 | 落ちた例の ID・期待値・実際の値・例外 | ── |
| テスト作成（支援モジュール） | 満たせなかった支援モジュールの例の ID・期待値・実際の値 | 実装 |
| モジュール設計 | 満たせなかった例の ID と、理由の種類（境界・粒度・組み立て）。前の設計 | **実装が返した値** |
| 要件定義 | 関門の指摘 | **実装が返した値** |
| レビュアー（定義の周） | 満たせなかった例の番号と、理由の種類 | **実装が返した値** |

実装の値を見せないのは、見せれば上の段がそれに合わせて「テストを緩めて通す」が、モデルを経由して戻ってくるからである。

### 何を変えてよいか

- **設計に戻っても、定義から来た例は変えられない**（設計の関門が定義と突き合わせる）。変えてよいのは分け方と、
  設計が自分で置いた例だけ
- **最初の定義は書き換えない。** 改良は改良ファイルに追記し、訂正も追記で行う（置き換えは許さない）。
  訂正された前の例は残し、テストから外す。訂正の追記が無いのに前の例が通らないものは関門が止める
- **概念ファイルの性質を覆う項目は取り下げられない。** 追記で訂正するだけで、訂正のあとも覆いが減っていないことを
  関門が見る。定義を緩めて通す経路にならないように
- **概念ファイルは改良では変わらない**（§6）

### 戻ったあとに何が無効になるか ── 続きから

設計に戻ってモジュールの境界を変えると、緑のモジュールの一部は意味を失い、一部は変わらない。
いまは戻るたびに、また通しをやり直すたびに、**全部のモジュールを作り直している**（2026-10-10 の迷路で、
組み立てにしか効かない直しのあと、緑の5つを 9B にもう一度作らせた）。改良の輪（§6）を回すには、これが重すぎる。

**緑になったモジュールに指紋を残す**（**未実装**）。指紋に入れるのは、自分の契約・doc・例、依存先をたどった全部、
使う型・エラー・共有の値、参照している概念ファイルの項目。次の通しや戻りで指紋が同じものは、9B に頼まず
前の実装を検証にかけ直して受け入れる（信用で通すのではなく、確かめて通す）。作り直すのは指紋が変わったものと、
それに依存するものだけ。これが「緑を取り消す」仕組みも兼ねる。

### 上限

試行（モジュールごと 3 回）、関門で同じ役に返す回数（3 回）、設計への戻り（2 回）に上限を置く。
値はいまの既定で、決まっていない（DECISIONS 未決 6）。上限に達したら人へ上げる。
外側の輪では、レビュアーへ戻す回数と、設計の周で designer へ戻す回数にも上限を置く（値は DECISIONS 未決 12）。
設計の周だけは、上限に達しても人へ上げず、分け直しを見送って次の観点へ進む（§6）。

## 6. 評価と改良 ── 外側の輪（未実装）

### 3つの輪

| 輪 | 問い | いま |
|---|---|---|
| 内側 | 実装は設計の例を満たすか | **閉じている**（赤 → 試行 → 緑、駄目なら再試行） |
| 中間 | 設計は実装できるか | **半分閉じている**（使い切ったら designer へ） |
| 外側 | できたものを、次はどう良くするか | **閉じていない**（人が開いて気づき、考え、直している） |

ループと呼べるのは、外側も機械が回すときである。いまの流れは、要求からアプリを一通り作ると終わる。
人がこのディレクトリで AI を使うときの「できた。次はこう良くしたい」に当たる役がいない。

### 1周目は MVP、そこから観点を一通り通す

```
 要求
  │
  ▼
 1周目：MVP（概念ファイル → 最初の定義 → 設計 → 実装 → 出力）
  │
  ▼
 ① 機能適合性 ─▶ ② 信頼性 ─▶ ③ 保守性 ─▶ ④ インタラクション能力 ─▶ ⑤ 性能効率性
   定義の周       定義の周      設計の周      定義の周                  定義の周
  │
  ▼
 一通り完成 ─▶ 人が実物を見る
```

- 1周目は MVP である。そこから、決まった**観点**を決まった順に1回ずつ通して、概念に沿って使い勝手を上げていく。
  **目的を満たしても止めない**
- 全部の観点を通したら**一通り完成**で、人が実物を見る
- 改良の向きは**改良ファイル**が担う。**概念ファイルには要求を分析した概念だけを書き**、目的・完成形・MVP の範囲は
  入れない。概念ファイルは改良では変わらない

### 観点

観点は**固定の一覧**で、**順番も固定**する。アプリごとに選ばせると、選ぶ側が観点を減らして早く「完成」できてしまう。
一覧はソフトウェアの品質特性の規格 **ISO/IEC 25010:2023** から選ぶ。自分で考えると、いま作っているもの（ゲーム）に
引っ張られるからである。この機構はゲームのためのものではない（§1）。

規格の特性を、次の条件でふるった:

- 案を出す役が、証拠から案を出せる
- 1回通せば済む（毎回確かめ続けないと崩れるものは向かない）
- 観点どうしが重ならない
- どのアプリにも当てはまる

| 順 | 観点 | 見ること | 案を出す役 | 入口の層 |
|---|---|---|---|---|
| ① | 機能適合性 | 必要なことができるか、正しいか、使う人の目的に合っているか | 評価役 | 定義 |
| ② | 信頼性 | 失敗に耐えるか、止まったあとに状態やデータを戻せるか | 評価役 | 定義 |
| ③ | 保守性 | 部品に分かれているか、副作用なしに変えられるか（機能の足しやすさ ── 拡張性 ── はここ） | **レビュアー** | **設計** |
| ④ | インタラクション能力 | 何ができるか分かるか、覚えられるか、操作しやすいか、誤りを防ぐか、誰でも使えるか | 評価役 | 定義 |
| ⑤ | 性能効率性 | 速さ、資源の使い方、扱える量の上限 | 評価役 | 定義 |

順番は「何があるか → それが壊れないか → 後の改良を入れやすく構造を整える → どう使えるか → 最後に最適化」。
インタラクション能力の改良は部品を増やしがちなので、その前に構造を整える。機能が固まる前の最適化は無駄になりやすい。

**観点にしないもの:**

| 特性 | 扱い |
|---|---|
| セキュリティ | 1回通しても後の改良で崩れるので、観点ではなく**毎回の検査**にする。出力の CSP とシェルの描き方は適合テスト（§7）、生成コードの参照は試行ごとの検証（§5） |
| 互換性・柔軟性 | 何で動くかはプラットフォームが決めるので、アプリの改良では動かない。量の上限は性能効率性の「容量」で見る |
| 安全性 | 人・財産・環境への害を避ける特性。今のプラットフォームはサンドボックスの中で、利用者のファイル・機器・外部に触れられないので、害の経路がほぼ無い。残る部分（誤った計算、確認なしの削除）は機能適合性とインタラクション能力で拾う。**サンドボックスの外に触れるプラットフォームを足すときは、安全性の手当てを持つことを足す条件にする** |

観点は全アプリに共通である。観点ごとに**証拠をどう集めるか**は、ソフトの種類で変わるので、プラットフォームの持ち物にする
（画面のあるものなら画面の記述や撮影、コマンドラインの道具なら入力と出力の記録。DECISIONS 未決 14）。

### 定義の周

外から見た振る舞いを変える観点（①②④⑤）の周。改良は定義から入る。

```
 評価役 ─ 動かした証拠を見て、その観点の改良案を出す（コードも定義も読まない）
  │
  ▼
 レビュアー ─ コードを読み、案を改良ファイルに書く（定義への追記）
  │
  ▼
 機械 ─ 最初の定義と改良ファイルから「今の定義」を作る
  │
  ▼
 designer → テスト生成 → 実装 ─┬─ 新しい例と前の例が全部緑 ─▶ 次の観点へ
                               │
                               └─ 緑にならない ─▶ レビュアーへ戻す
```

- **1つの観点につき1回。** 評価役はその観点で1回に出せるところまで出し、それを実装する。評価役へのブリーフは
  その観点での改良を求めるだけにし、「出し尽くせ」や件数の指定のような不自然な指示はしない
- 評価役が案を出し、実装が緑になれば、その観点は通したとする。**「本当に良くなったか」を別に判定する段は置かない。**
  後の観点が前の観点の成果（評価でしか確かめられないもの）を崩すことは、一通り完成したときに人が実物を見て拾う
- 案は証拠に基づくものだけにする（「最初の画面の 90% が単色」は案の根拠になるが、「なんとなく地味」はならない）
- 証拠は箱の中で、生成コードを動かせる exec として集める。3D なら WebGL の描けるブラウザが要る（DECISIONS 未決 11）

### 設計の周

中の作りの観点（③保守性）の周。外から見た振る舞いは変えないので、**定義は変えず、設計だけやり直す。**

```
 レビュアー ─ コードと設計を読み、変えにくいところを指摘する
  │            （例：値段の計算と表示の整形が1つの部品に混ざっている）
  ▼
 designer ─ 指摘を受けて、部品の分け方を直した設計を書く（定義と、定義から来た例はそのまま）
  │
  ▼
 テスト生成 → 実装 ─┬─ 前の例が全部緑 ─▶ 成功、次の観点へ
                    │
                    └─ 緑にならない ─▶ designer へ戻す。上限に達したら、分け直しは見送り、前の設計のまま次の観点へ
```

振る舞いを変えない周なので、見送っても何も失わない。

### 改良ファイル

**最初の定義は書き換えない。** 改良は別の改良ファイルに積む。原本が残り、何をなぜ変えたかが改良ファイルの並びとして残る。

- **追記だけ。置き換えは許さない。** 訂正も追記で行う。上書きより、追記で訂正されていくほうが、AI にとって
  何が変わったかが分かりやすい
- 訂正の追記は、どの番号を訂正したかを構造化された欄に持つ。訂正された前の例は消さずに残し、テストから外す。
  訂正の追記が無いのに前の例が通らないものは、関門が止める
- 情報量は絞り、コンテキストを小さく保つ。形は DECISIONS 未決 16

### 改良が緑にならないとき

行き詰まった段の1つ上へ戻す。内側の輪（使い切ったら設計へ）と同じ形である。

- 定義の周で緑にならなければ、**レビュアーへ戻す**。渡すのは満たせなかった例の番号と理由の種類だけで、
  実装が返した値は渡さない（§5「戻すときに渡すもの」）。レビュアーは訂正を追記するか、その改良を取り下げる
- **取り下げてよいのは改良で足したものだけ。** 概念ファイルの性質を覆っている項目は、最初の定義のものでも改良で
  足したものでも取り下げられず、追記で訂正するだけ。訂正のあとも覆いの関門が、その性質がまだ覆われているかを
  確かめる。本質かどうかはレビュアーに判断させず、概念ファイルとの対応（番号）で機械が決める
- 1周目も同じ扱いにする。最初の定義が緑にならなければ、definer に同じ形で返し、訂正を追記させる
- 戻す回数には上限を置き（DECISIONS 未決 12）、達したら止まって人へ上げる
- 「捨てて次の改良へ」は採らない。最初の定義の本質的な部分が実装できないまま消えていくからである

### 人が入るところ

- **一通り完成したとき**: 実物を見る
- **必要なリソースが無いとき**: 「それを用意するか、その機能を入れないか」を問う。何をリソース不足とするか
  （箱に無いライブラリや素材・外への通信、プラットフォームの力、モデルの力、予算）、返事を待つあいだ輪をどうするかは
  DECISIONS 未決 15

エンジン自体の誤り（迷路の1回目の「ブリーフが文脈に入らない」など）は、どの段に戻しても直らない。
「エンジン」と判定して人に返す（§5）。

### 機械で守らせること

- **自己完結の関門**: 文書の中の文章による参照（「D1で定めた」「相当」「上記」「前述」、他の項目やモジュールの
  ID を指す散文）を指摘にする。概念ファイルの番号による参照は、構造化した欄に書くので別扱い
- **覆いの関門**: 概念ファイルの各性質と要件が、定義の例か評価の基準のどちらかで覆われているか。改良のあとも減っていないか
- **単独で読ませる確認**（DECISIONS 未決 13）: 一つの層の文書だけを、上を知らない別の役に渡し、
  「何を作り、どう合否を判定するか」を答えさせる。答えが元の意図とずれていれば、その文書に欠落がある

## 7. 言語とプラットフォーム

### アダプタ ── 本体は言語を知らない

言語ごとの差は**アダプタ**に閉じ込める。新しい言語は、アダプタを1つ足して適合テストを通せば使える。
旧い形のランナーは言語の分岐を本体に持ち、Python の文法が言語に依らない規則の顔をして入り込んでいた箇所が
run 1〜8 で6回見つかった。本体が言語を知っている限り、これは繰り返す。

| | 内容 |
|---|---|
| 型の写像 | 設計の型（int / float / string / bool / list / map / record / enum / optional / error）→ その言語の型 |
| 型の生成 | **record・enum・error の定義は機械が生成する。** solver が書くのは関数の中身だけ |
| スタブ生成 | 契約から、形は正しく値は番兵の実装を生成する。番兵は設計の全期待値と衝突しないものを機械が選ぶ |
| テスト生成 | 設計の例から、値を作り・呼び・比べるテストを生成する |
| 比較関数 | `example` / `check` / `check_raises`。値を正規形に直し、記録を書き出す |
| 実行 | テストを1つずつ隔離し、時間制限つき・ネットワーク無しで走らせるコマンド |
| 参照の列挙 | モジュールのファイルが参照する他モジュールと、使っているグローバル（参照の検査用、§5）。言語ごとの別ファイル（`refs.mjs`・`refs.py`）で、構文解析して読む。**使ってよいグローバルの一覧**もここに持つ |
| 実装の手引き | solver のブリーフに載せる、その言語での書き方 |

言語に依らない中核（設計の読み込み、作る順序、例のファイル、番兵の材料）は `adapters/design.py` にある。
判定は比較関数の記録から読むので、走らせ役のテストフレームワークに求めるのは
**「テストを1つずつ隔離して走らせる」ことだけ**になる。

### 適合テスト

**アダプタを足すとは、適合テストを通すことである。** アダプタは見本の設計（放置ゲーム、コイン集め）を受け取って
テストを生成し、正しい実装では全部緑、スタブでは結果を観測する例が**比較で**赤（クラッシュは 0）、
1か所の誤りではその誤りで期待値が変わる例だけが赤、になることを確かめる。生成したテストが全言語で
同じ例を同じように判定することも、ここで確かめる。

**プラットフォームの安全も適合テストで確かめる**（`engine/tests/test_csp.py`）。出力に CSP が付いて外へ通信できないこと、
シェルが文字を文字として描くこと（`innerHTML` などを使わない）。CSP はページに埋め込んだ1つのスクリプトだけを
**ハッシュで**許し（`build-app` が束ねたあとで埋める）、ほかの経路で入ったスクリプトは動かない。どちらもアプリや周ごとには変わらないプラットフォームの持ち物なので、
プラットフォームを作ったとき・変えたときに1回確かめれば足りる。毎回変わる生成コードの参照は、試行ごとの検証で見る（§5）。
サンドボックスの外に触れるプラットフォーム（③など）を足すときは、安全性の手当て（取り返しのつかない操作の前の確認、
安全な範囲の制限など）を持つことを足す条件にする（§6「観点にしないもの」）。

### 対応する言語

箱に入っていて、走らせ役を確かめたもの（2026-10-09）。アダプタがあるのは Python と TypeScript。

| TypeScript / JavaScript | Node 22 | vitest |

### プラットフォーム ── 汎用シェル

プラットフォームは `adapters/platforms/<名前>/` に、次を持つ:

| ファイル | 中身 |
|---|---|
| `platform.json` | 定義が持たなければならない型と関数（`start`・`step`・`act`・`screen`・`save`）、definer のブリーフに載せる文（`brief`）、単位や向きの約束（`conventions`） |
| `shell.ts` | 汎用シェル。アプリの5つの関数だけを呼び、画面の記述を DOM や three.js に描く。保存は localStorage |
| `page.html` | 1つの HTML の雛形。束ねたスクリプトを埋め込む |
| `boot.mjs` | 起動確認。happy-dom で開き、描けること・押せるボタンや決まった入力で壊れないことを確かめる |

definer のブリーフは、選ばれたプラットフォームの `platform.json` が言うことだけを言う。形の詳細は FORMATS §6。

出力は窓口の `build-app` が作る: 組み立てモジュールとシェルを rolldown で1つのスクリプトに束ね、`page.html` に
埋め込み、起動確認にかける。どちらも exec として走る。
