# DECISIONS.md — 決まったことと、決まっていないこと

設計の判断の記録。今の設計そのものは [DESIGN.md](DESIGN.md) と [SYSTEM.md](SYSTEM.md) にあり、それだけで読める。
ここは「いつ、何を、なぜ決めたか」を後から引くためにある。後の決定で前の決定が変わったときは、
前の決定を消さず、後の決定にそう書く。

---

## 決まったこと

2026-10-09 から。番号は日付順で、振り直さない。

1. **デバッグは「落ちた場所が、悪い段を指す」形にする**（DESIGN §5）。期待値はテストに書かせず、
   テスト側のロジックは支援モジュールにし、整合は各段の出口で確かめる
2. **テストは機械が生成する。** 設計の例はデータなので、アダプタが言語ごとに書き写す（FORMATS §8-1）。
   新しい uid `tester`（Claude、planner とは分ける）は支援モジュールの中身だけを書く。
   当初は「テストは Claude が書く」と決めたが、例が言語に依らないデータで書けると分かって改めた
3. **テストの実行は新しい uid `exec`** で行う
4. **言語はアダプタ方式。** WSL に入っている言語に最初から対応する（DESIGN §7）
5. **上流は、定義と設計を別の uid にする。** 設計の関門は「設計が定義の例を含んでいるか」を
   突き合わせるので、同じ主体が両方を書くとこの突き合わせが形だけになる
6. **Claude の役は通信の宛先を絞らない。** 道具（Read / Write / Edit のみ）で外への手段を剥奪する（SYSTEM §8-3）
7. **プロビジョンを作り直す**（SYSTEM §8）。機械と作業場を分け、役を1つの表から生成し、通信を役ごとに制限し、SSH の鍵では窓口しか開かない
8. **過去の run は残さない。** run 1〜8 の成果物は退避せず、箱を作り直すときに消す。適合テストは run 8 の
   S4・S5 の**形**を写して作る
9. **Java・PHP・C/C++ の走らせ役は、フレームワークをプロビジョンで入れる。** JUnit 5・PHPUnit・
   GoogleTest（`provision/36-languages.sh`）。各言語の標準的な仕組みを使い、アダプタを薄く保つ
10. **役の構成。** planner を廃止し、definer（1007）と designer（1008）を作る。critic は残す。
    要件分析は、未決の 1 が決まるまで definer が担う
11. **solver はローカルモデルだけ。** 通信は loopback の 8080（llama-server）だけ。外へ通信が要る
    codex の予備は外した
12. **作業場に書けるのは窓口だけ。** 役は自分の `out/` に書き、窓口が検査して写す（SYSTEM §8-5）
13. **保守の入口（既定ユーザー）は、窓口の制限の外に残す。** ループからは使わない
14. **目的は、開けばそのまま動くアプリを1つの HTML ファイルで出力すること**（DESIGN §1）。ブラウザの
    サンドボックスの中で動かし、生成コードをホストで直接動かさない
15. **プラットフォームはまず `browser-dom`（①）と `browser-3d`（②・three.js）。** 静的サイト・
    Next.js・デプロイ（③）は後で。ライブラリはプラットフォームごとにプロビジョンで版を固定して入れる
16. **画面は汎用のシェルが描く。** アプリは画面の記述（データ）を返し、プラットフォームごとに機械側が
    用意するシェルがそれを描く。アプリごとの確かめられないコードを作らない
17. **browser-dom の画面の形を固定した**（2026-10-10、FORMATS §6）。アプリは `start`・`step`・`act`・`screen`・
    `save` の5つを持ち、`screen` は `Screen {title, nodes: list<Node>}`、`Node {kind: heading|text|button,
    text, action, enabled}` を返す。汎用シェルはこれだけを呼んで縦に並べて描く
18. **browser-3d の画面の形を固定した**（2026-10-10、FORMATS §6）。関数は同じ5つで、`step` が毎フレーム
    `Input {keys, mouse_dx, mouse_dy, locked}` を受け、`screen` が `Scene {title, camera, objects, hud}` を返す。
    物は箱・球・板・円柱の単色だけ、光・影・空はシェルの持ち物。単位と向きの約束（fov だけ度）は
    `platform.json` の `conventions` が正本で、definer のブリーフにもそのまま載る。プラットフォームごとの
    ブリーフの文も `platform.json` の `brief` に移した（ブリーフはプラットフォームの言うことだけを言う）
19. **プラットフォームはアプリの持ち物。** 要件からのアプリは作るときにプラットフォームを選び
    （`app.json` の `platform`、CLI の `--platform`、ダッシュボードの「形」）、definer はそのブリーフを受け取る。
    別のプラットフォームの定義は定義の関門の指摘として返る
20. **要求分析の層を最初に置く**（2026-10-10、DESIGN §4。未決 1 はこれで決着: 分ける）。人が書くのは**要求**、
    分析が出すのが**要件**と**概念ファイル**、それを機械が確かめられる約束にするのが**要件定義**
21. **各層の文書は、それだけで完結する。** 上の層の文章を参照して意味を省かない（「D1で定めた」「相当」
    「上記」を書かない）。全体の意味は、分けた層が持ち続けて、組み合わせが自分の受け取った仕様を
    満たすことを確かめる（工場の部品のマニュアルと、組み立ての検査）
22. **概念ファイル（`concepts.json`）は全員が番号で参照する。** 要求分析が一度だけ書く原本で、言い換えない。
    要件と範囲外もこのファイルに持つ（**原本は1つ**）。形のたたき台は FORMATS §11。
    参照は文章ではなく番号で書き、弱い役にはエンジンが参照先を本文に展開して渡す。
    概念ファイルの性質がどこで確かめられるか（定義の例か、評価の基準か）を関門が見る
23. **外側の輪を機械が回す**（DESIGN §6）。 できたものを評価して、悪い段へ指摘で戻す。人間は分析を確かめる
    （最初）と、輪が止まったあとに好みで決める（最後）
24. **言葉: 要求・要件・要件定義を分ける。** アプリの置き場の `requirements.md` とダッシュボードの「要件」は
    人が書くものなので**要求**に改める

## 決まっていないこと

番号は振り直さない。決まったら取り消し線を引き、どの決定で決まったかを書く。

1. ~~要件分析と要件定義を分けるか~~ → **分ける**（決定 20）。残るのは**分析役を誰にするか**:
   新しい uid か、どのモデルか。人の確認を、分析ができた時点で必須にするか
2. **上流を誰が書くか。** uid は定義と設計を分けると決めた（決定 5）。分析は 1
3. **各段の出力形式。** `definition.json` と `design.json` は**たたき台がある**（[FORMATS.md](FORMATS.md)）。
   run 7 の放置ゲームで書き、試作の関門と汎用の実行器にかけて確かめた。分析の出力は概念ファイル1つ
   （要件も中に持つ）と決め、形の**たたき台を書いた**（FORMATS §11）。迷路で書いて関門にかけて確かめる
4. **例で表しにくいもの。** 不変性は「呼んだあとで入力を観測する」で書けた。I/O・時計・画面は
   v1 ではシェルに寄せる案（FORMATS §6・§9）。状態を持つオブジェクトとコールバックは v1 では持たない案
5. **粒度の基準。** どこまで分割すれば弱いモデルの範囲に収まるか。「使い切り → 粒度」が起きた回数がその手掛かりになる
6. **試行回数と戻りの上限の値**
7. **窓口の残りの操作の中身。** `prepare-tests`・`verify`・`accept` は決めて実装した（SYSTEM §4）。`run-role` と `attempt` の引数と返す形は、それぞれを作るときに決める
8. **数を文字列にするときの丸め。** 言語ごとに既定が違う（FORMATS §8-3）。設計が文で宣言する以上の
   仕組み（型や関門）が要るか
9. **汎用のシェルで描けないもの。** 画面の記述の語彙（今は見出し・文・ボタン）に無い表現が要るとき、
   語彙を広げるのか、アプリ固有のシェルを許すのか。②（browser-3d）の形は決めた（決定 18）が、
   物の形（箱・球・板・円柱）と単色だけで足りないとき（模型の読み込み、質感、音）も同じ問い
10. **評価役は誰か、共通の基準の中身。** critic を評価役にするか。「何をするか分かる」「見分けられる」などの
    質の概念を、どこまで具体的に、どのプラットフォームにも共通の形で書くか（DESIGN §4・§6）
11. **証拠を撮る環境。** 箱の中に WebGL の描けるブラウザを入れ、exec として動かす方法（DESIGN §6）
12. **外側の輪の上限と止まる条件の値。** 何回まで改良するか、「良くならない」をどう判定するか
13. **単独で読ませる確認をするか。** 一つの層の文書だけを、上を知らない役に渡して「何を作り、どう合否を
    判定するか」を答えさせる。費用に見合うか（DESIGN §6）
