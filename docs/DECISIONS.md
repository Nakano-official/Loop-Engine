26. **外側の輪の役の構成**（2026-10-13、決定 25 による）:
    - **分析役**（新しい uid、Claude）: 概念ファイルだけを書く。未決 1 の「分析役を誰にするか」はこれで決着

      コードは**読むだけ**。改良役を別に作らないのは、改良が定義から始まり、分ける理由が無いため
    - **designer**: 今のまま。決定 5（定義と設計を分ける）は維持する
    - **tester**: 残す。支援モジュールは実装を確かめる側のコードで、弱いモデルが書いた**甘い偽物は、

      実装は支援モジュールが初めて要るときに行う
    - **評価役**: critic の uid を使う。観点（決定 30）ごとに、動かした証拠を見て**改良案を出す**。
      読むのは概念ファイルと証拠で、コードも定義も読まない。未決 10 の「評価役は誰か」はこれで決着
27. **改良は定義から始め、最初の定義は書き換えない**（2026-10-13）。改良は別の**改良ファイル**に積む。
    原本を残し、何をなぜ変えたかを改良ファイルの並びとして残すため
    - **置き換えは許さない。訂正は追記する。** 訂正の追記は、どの番号を訂正したかを持つ。訂正された前の例は
      消さずに残し、テストから外す。訂正の追記が無いのに前の例が通らないものは関門が止める。
      上書きより、追記で訂正されていくほうが AI にとって何が変わったかが分かりやすい
    - コンテキストは小さく保つ。改良ファイルの情報量は絞る
    - 概念ファイルは改良では変えない
28. **改良が緑にならないときは、レビュアーへ戻す**（2026-10-13）。行き詰まった段の1つ上へ戻す、という
    内側の輪と同じ形にする。渡すのは満たせなかった例の番号と理由の種類だけで、実装が返した値は渡さない
    （DESIGN §5「戻すときに渡すもの」と同じ理由）。レビュアーは訂正を追記するか、その改良を取り下げる。
    戻す回数には上限を置き、達したら止まって人へ上げる
    - 取り下げてよいのは改良で足したものだけ。**概念ファイルの性質を覆っている項目は取り下げられず**、
      追記で訂正するだけ。訂正のあとも覆いの関門が、その性質がまだ覆われているかを確かめる。
      本質かどうかはレビュアーに判断させず、概念ファイルとの対応（番号）で機械が決める
    - 1周目も同じ扱いにする。最初の定義が緑にならなければ、definer に同じ形で返し、訂正を追記させる
    - 「捨てて次の改良へ」は採らない。最初の定義の本質的な部分が実装できないまま消えていくため
29. **目的を満たしても止めない**（2026-10-13）。1周目は MVP で、そこから概念に沿って使い勝手を上げ続ける。
    **概念ファイルには要求を分析した概念だけを書き、目的・完成形・MVP の範囲は入れない。** 改良の向きは
    改良ファイルが担う。決定 23 の「人は最後に好みで決める」はこの決定と決定 31 で置き換える
30. **完成は、固定の観点を一通り通したとき**（2026-10-13）
    - 観点（UI、拡張性など）は**機械側で固定の一覧**を持ち、**順番も固定**する。アプリごとに選ばせると、
      選ぶ側が観点を減らして早く「完成」できてしまう。順番を固定するのは安定のため
    - **1つの観点につき1回。** 評価役がその観点で1回に出せるところまで出し、それを実装する。
      評価役へのブリーフはその観点での改良を求めるだけで、「出し尽くせ」や件数の指定のような不自然な指示はしない
    - 評価役が案を出し、実装が緑になれば、その観点は通したとする。「本当に良くなったか」を別に判定する段は置かない。
      後の観点が前の観点の成果（評価でしか確かめられないもの）を崩すことは、完成のときに人が実物を見て拾う
31. **人が入るのは、一通り完成したときと、必要なリソースが無いとき**（2026-10-13）。リソースが無いときの
    問いは「それを用意するか、その機能を入れないか」
32. **観点は ISO/IEC 25010:2023 の品質特性から選ぶ**（2026-10-13）。自分で考えると、いま作っているもの
    （ゲーム）に引っ張られるため。条件でふるう: 案を出す役が証拠から案を出せる、1回通せば済む、重ならない、
    どのアプリにも当てはまる。一覧・順番・案を出す役・入口の層は DESIGN §6
    - 順番: 機能適合性 → 信頼性 → 保守性 → インタラクション能力 → 性能効率性。何があるか → 壊れないか →
      後の改良を入れやすく構造を整える → どう使えるか → 最後に最適化
    - **観点ごとに入口の層を決める。** 外から見た振る舞いを変える観点は定義から入る（**定義の周**）。
      中の作りの観点（保守性）は設計から入る（**設計の周**）。保守性だけを特別なループにするのではなく、
      輪は1つで、入口の層が観点の性質で決まる
    - 保守性はコードの性質なので、案を出すのはコードを読むレビュアー。ほかの観点は評価役。
      拡張性（機能の足しやすさ）は保守性の修正性・モジュール性として扱う
33. **設計の周は、定義を変えずに設計だけやり直す**（2026-10-13）。レビュアーが変えにくいところを指摘し、
    designer が分け直す。外から見た振る舞いは変わらないので、**前の例が全部緑なら成功**。緑にならなければ
    designer へ戻し、上限に達したら**分け直しは見送り、前の設計のまま次の観点へ進む**。振る舞いを変えない周
    なので、見送っても何も失わない（決定 28 の「本質が消える」は起きない）
34. **セキュリティは観点にせず、検査として毎回かける**（2026-10-13）。1回通しても後の改良で崩れるため。
    今の箱の守り（uid・権限・通信の制限）は作っている最中の機械を守るもので、箱の外で開かれる出力
    （`app.html`）を開く人は守らない。検査は2つに分ける
    - **出力の CSP とシェルの描き方**は、アプリや周ごとには変わらないプラットフォームの持ち物なので、
      プラットフォームを作ったとき・変えたときにアダプタの適合テストで確かめる
    - **生成コードの参照**（宣言外のモジュール、許可していないグローバル ── `fetch`・`document`・`eval` など）は、
      9B がコードを書くたびに変わるので、**試行ごとに `verify` の中で**確かめ、違反はその試行を棄却して実装へ戻す。
      CSP は開いた人のブラウザで止める仕組みで、`document` への書き込みは止められず、止まっても理由が分からない。
      参照の検査は作る段階で見つけて悪い段へ戻す仕組みで、両方要る
35. **互換性・柔軟性・安全性は観点にしない**（2026-10-13）。互換性と柔軟性は、何で動くかをプラットフォームが
    決めるので、アプリの改良では動かない（量の上限は性能効率性の「容量」で見る）。安全性（人・財産・環境への害を
    避ける）は、今のプラットフォームがサンドボックスの中で利用者のファイル・機器・外部に触れられないので、
    害の経路がほぼ無く、残る部分（誤った計算、確認なしの削除）は機能適合性とインタラクション能力で拾える。
    **サンドボックスの外に触れるプラットフォームを足すときは、安全性の手当て（取り返しのつかない操作の前の確認、
    安全な範囲の制限など）を持つことを、足す条件にする**
36. **機構は汎用。ゲームは実験の場**（2026-10-13）。いまの題材がゲームなのは、できたものを確かめやすいから
    で、ゲームを作ることは目的ですらない。観点などの決まりはゲームのためではなく、どのソフトにも当てはまる
    形で決める。プラットフォームの関数（`start`・`step`・`act`・`screen`・`save`）や、ダッシュボードの
    「遊ぶ」のようにゲームに寄っているところは、いずれ見直す
37. **純粋なモジュールが使ってよいものは、言語ごとの一覧で決める**（2026-10-13、決定 34 の実装）。許すものを
    列挙し、それ以外は全部棄却する（禁止の一覧だと、書き漏れたものが通る）。一覧は言語の組み込みの計算の道具
    （TypeScript なら `Math`・`JSON`・`Array`・`Map` など、Python なら計算する組み込みと標準ライブラリ）で、
    プラットフォームの知識は要らないので、アダプタの別ファイル（`refs.mjs`・`refs.py`）に持つ。窓口の `verify` が
    それを呼ぶ（流れは pipeline だけ、言語の差はアダプタだけ ── SYSTEM §6、DESIGN §7）
    - **`Date` と `Math.random`（Python の `time`・`datetime`・`random`）も禁止する。** 呼ぶたびに結果が変わるので
      例で確かめられない。時刻も乱数も、呼び出す側（シェル）から引数で受け取る。乱数が要るアプリには、シェルが
      種を渡す仕組みが要る（まだ無い）
    - 参照は正規表現ではなく構文解析で読む。TypeScript は凍結したツールチェーンの rolldown の構文解析を使い、
      新しいパッケージは入れない。読むだけで実行しないので、runner が自分で読む
    - 試行を使い切って全部が「使ってはいけないもの」なら、設計の境界の誤り（要るものを引数で渡していない）として
      designer へ戻す
